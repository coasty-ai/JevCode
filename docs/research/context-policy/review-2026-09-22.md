## Defects

### D1 [blocker] The zero-cost read makes the tail of any file > 32 KiB permanently unreachable
`src/loop/context/context-cache.ts:311-330`, `src/provider/prompts.ts:341-344`, `src/loop/stages/execute.ts:86-91`.
`filesInViewSection` shows ≤ `FILE_VIEW_MAX_CHARS` (32 KiB) and appends `…[N more bytes not shown of B; full file:
<path>]…`. The generator follows the hint with `read <path>`; `execute.ts` consults `ctx.contextReads.unchanged(p)`
first, which sees the path in `this.loaded` with an unchanged stat and answers `unchanged since step N (sha …); contents
are under Files in view`. The rest of the file is never obtainable and three identical reads trip the loop detector.
Reproduced end-to-end (40 KiB `big.py`, three `read big.py` steps): steps 2 and 3 both refused. This is the structural
re-read loop §8 exists to remove (`glm-jev-off-baseline.md:224-231`).
**Fix:** `unchanged()` returns null when `LoadedFile.truncatedBytes > 0` (or the caller asks past the shown window);
better, return the next window (`[lines a–b of N]`, §8.4) rather than refusing.

### D2 [blocker] The zero-cost read claims "contents are under Files in view" for a file the prompt says is not shown
`context-cache.ts:311` vs `:260-272` / `prompts.ts:337-339`. `refresh()` marks entries past `fileCacheBytes`
`omitted: true` (content `''`) and the prompt renders `— not shown (files budget); read it if you need it`;
`unchanged()` cannot see `omitted` and still answers from `this.loaded`. Same at shrink `level >= 1`.
**Fix:** pass the last build's shown/omitted set into `ContextReadHooks.unchanged`; refuse the short-circuit for anything
not actually rendered.

### D3 [blocker] `unchanged()` poisons the stat cache, so a content change past the shown window is never re-read
`context-cache.ts:316-325` (`cur.stat = st`). On a stat mismatch it re-reads only `maxFileChars` and compares the hash of
that prefix; on a match it writes the new stat without updating content, and `load()` short-circuits on `sameStat`
forever. Reproduced (100 KiB file, edit at byte ~40 960, same size): the prompt keeps the pre-edit window.
**Fix:** never write `cur.stat = st` unless the whole file's digest matched (or `truncatedBytes === 0`); on any stat
mismatch of a truncated file, invalidate.

### D4 [blocker] `read jevcode:…` bypasses the execute stage's read budget — 392 KB from one step
`execute.ts:75-84`: the `jevcode:` branch does `total += shown.length` but never checks
`total + shown.length > CONTEXT_MAX_TOTAL_BYTES` before pushing. Reproduced: 14 `jevcode:` paths → a 392 082-char read
output stored whole; repeated every step it fills the 64 MiB per-run cap in ~170 steps.
**Fix:** the same guard as the workspace branch; raise the caps to §8.5's 16 files / 32 KiB / 128 KiB (D13).

### D5 [blocker] `jev-only` / `llm-jev`: all the §8 bookkeeping runs, nothing reads it, and the meter never moves
`engine.ts:2299-2300` (third `runProposeStage` call site not converted), `:3145` (`commitContext` mode-agnostic).
In jev-only/llm-jev the engine writes `outputs/step-n.txt` per step, `context/summary.json`, a 12-entry `history`, and a
compaction at step 8 while `runSynthStage` never receives a context view (`SynthesisContext.contextText` unimplemented).
`status().context` reports `ctx 0%` for the life of every such run and the 85 % trigger is dead in those modes.
**Fix:** gate `commitContext` on the modes that consume it (or implement §8.8's third column), convert the `:2299` call
site to `proposeWithContext`, add the jev-only/llm-jev cadence point.

### D6 [blocker] `readContextExtension` validates shape but not content — a mirrored `state.json` crashes the prompt build and injects sections
`src/checkpoint/types.ts:41-68`. `judge` cast unchecked (`judge: {}` → `TypeError … toFixed` in `entryHeader` on every
prompt build of the resumed run); `intent`/`outcome` cast into unions with no membership check; `action`, `output`,
`notes[]`, `shownFiles[]` unbounded (a 5 MB `output` round-trips into `state.json`, 38 ms per build); a restored
`history[0].action` carrying `\n\n## Your reply … ## Task` yields two `## Your reply` sections in the prompt.
**Fix:** validate `judge` member-by-member, check the unions, clip free text to §8.3 bounds at read, cap array lengths,
neutralise leading `#` in restored free text rendered outside a fence.

### D7 [blocker] `contextPolicy` is unreachable outside tests — finding 28's pin does not exist
`src/loop/context/types.ts:120-135`, `engine.ts:788`. `EngineOptions` has no `contextPolicy`; the engine reads it through
a cast; no config key, no CLI flag, no bench plumbing. Default `'relaxed'` silently changes every bench arm's prompt shape.
**Fix:** `contextPolicy?: ContextPolicyOptions` on `EngineOptions` (contract 1.4 block), a `context.*` config block
(TUI-owned), and a bench pin (`view:'legacy'` for the frozen arms).

### D8 [major] §8.2 money term missing; floor raised 60k → 120k, exceeding a small model's window
`src/loop/context/limits.ts:13-21`. Spec: `clamp(min(tokens × 3.4 × 0.55, (spendCapUsd × 0.5 / (maxSteps × inputPerM))
× 1e6 × 3.4), 60k, 800k)`. Code: `clamp(tokens × 3.4 × 0.55, 120k, 800k)`; the doc comment states the wrong formula.
`contextBudgetChars(32_000) = 120_000 chars ≈ 35.3k tokens` > the whole 32k window; `meter.ts:42` hides it.

### D9 [major] `generatorContextTokens` never passed — `windowTokens` hardcoded 128k
`engine.ts:788` omits the second argument; `budgetChars` is always 239 360. `engine-context.test.ts:193` pins the bug.

### D10 [major] §8.2 fill order inverted; the test asserts the wrong order while citing §8.2
`prompts.ts:460-476`, `prompts-context.test.ts:70-72`. Spec: `… kept → files in view → recent steps → summary → other
sessions → candidates`. Code: `summary → files → candidates → recent`, with the summary surviving longest. Absent:
`## Kept (do not re-derive)`, `## Other sessions`.

### D11 [major] No tier degradation ladder; fit not computed before the read
`history.ts:153-170`, `prompts.ts:359-370`. §8.2(a) requires 32 KiB → `headTail(12k, 4k)` → 600-char body → one-liner,
costed from `fullOutputChars` before any read; §8.2(c) clips the newest to 16k at the floor. Neither exists;
`ensureContextLoaded` reads up to 6 output files unconditionally. At `budgetChars: 60_000` with 12 × 60 KiB outputs the
prompt is 5 308 chars — every output a one-liner, every file omitted. No `/context` recent-steps line.

### D12 [major] Mid-run eviction by the 64 MiB bound is not recorded — the pointer dangles until the next resume
`store.ts:416-458` (`boundOutputsDir` unlinks silently), `engine.ts:2728-2742`. `outputEvicted` does not exist;
`missingOutputs` populated only after a resume; `runOutput`'s memoised fallback passes `ref: null` so that clip has no
recovery path.

### D13 [major] §8.5's read-cap rise not applied
`execute.ts` still uses 12 / 16 KiB / 60 KiB from `stages/context.ts`; §8.5 says 16 / 32 KiB / 128 KiB in
`core/limits.ts`. With D1 an ordinary read shows less (16 KiB) than the prompt already shows (32 KiB).

### D14 [major] Perf claims not gated where they matter; the one new gate is load-flaky
`perf/step-overhead.ts` untouched (no `promptBuildMs` row, no §8.3 cold-start row); `RefreshResult.ms` discarded by
`contextView`; the `prompts-context.test.ts:135` gate measures `buildPrompt` alone and produced 7.67 ms vs `< 5` inside a
full run; `engine-perf` harnessMs duplicated (legacy 63.3, relaxed 58.0, budget 50 under load).

### D15 [major] Meter arithmetic
After a compaction `promptChars` is reduced by persisted-JSON + summary chars, not prompt chars; the `context:compacted`
line reports the same unrelated units; the system prompt (≤ 32 KiB) is not counted; `windowTokens: Math.max(...)`
inflates a small window instead of surfacing it.

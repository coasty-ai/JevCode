# 12 — Accessibility, internationalisation, robustness and testing strategy for the JevCode TUI

Research notes for the chat-style TUI (composer, slash commands, sessions, steering, review prompts, Jev decisions view) that will sit on the existing engine. Every claim carries its source and the fetch date; local sources are the installed files under `node_modules/` (ink 7.1.1, react 19.3.0, ink-testing-library 4.0.0) and the repo itself, checked 2026-09-20 on Node v22.23.2 / macOS 26.6.2 (Darwin 25.6.0). Microbenchmarks were run from `/tmp/jev-tui-bench` against the repo's `node_modules`; their scripts are described inline so they can be re-run. Items that could not be verified are marked **UNVERIFIED** with what was tried.

Companion notes: `docs/research/01-ink-stack.md` (Ink internals, throttling, ink-testing-library semantics) and `docs/research/05-cli-architectures.md` (Gemini CLI / Codex / opencode structure). This file does not repeat them; it cites them where they already settle a point.

## 0. Where the current TUI stands (facts that constrain the design)

- `src/tui/App.tsx` renders one `<Static>` transcript above a `rows − 2` height-budgeted dynamic region (rule, 2-line live region, ≤ 12 decisions, confirmation box, 1-line status with a 125 ms braille spinner `SPINNER_FRAMES = ['⠋','⠙',…]`, `SPINNER_INTERVAL_MS = 125` in `src/tui/StatusLine.tsx`); `render({ exitOnCtrlC: false, patchConsole: false })`; one `useInput` gated by `Boolean(isRawModeSupported)`; keys handled: `Ctrl-C`, `y`, `n` (local read, 2026-09-20).
- `src/tui/useEngine.tsx`: 50 ms (≤ 20 fps) live-region coalescer, `LIVE_BUFFER_MAX = 64 * 1024`, `DECISIONS_KEPT = 12`, event bus with `BUS_REPLAY_MAX = 10_000`. `src/tui/plain.ts`: `TRANSCRIPT_TEXT_MAX = 600`, `TRANSCRIPT_DETAIL_MAX_LINES = 60`, `TRANSCRIPT_DETAIL_MAX_CHARS = 6000`, `sanitizeStream` strips C0/DEL/C1 (`/[\u0000-\u0008\u000b\u000c\u000e-\u001f\u007f-\u009f]/g`) so command output "cannot clear the screen, move the cursor or write the clipboard" (local read).
- Perf gates already measured (`perf/results/latest.json`, 2026-09-20T05:24Z): first frame cold median 89.0 ms / p95 89.9 ms (gate 300); render lag rows 40: p95 3.24 ms, max 3.26 ms, `clears: 0`; rows 12: p95 2.14 ms, `clears: 0`.
- **Hard-constraint hazard found:** `src/tui/App.tsx:125-127` writes every keystroke to the opt-in trace file: `` `… tui.useInput input=${JSON.stringify(input)} ctrl=${key.ctrl} …` `` when `JEVCODE_TRACE` is set. Today `input` is only `y`/`n`/`c`, but once a composer exists this line would log typed text (API keys pasted into a prompt, for example). It must change to log a key *category* (`printable`, `ctrl`, `paste(n chars)`) before the composer lands (local read, 2026-09-20).
- Live pty captures under `scripts/demo/tui-run.exp` (11 `tui-pty*.log` files in `docs/live/`, 18.6 MB total): `ESC[2J` = 0, `ESC[3J` = 0, `ESC c` = 0 in every file; `ESC[?2026h` (synchronized-update begin) 193–8,729 per run, i.e. one pair per frame; `ESC[?25l` exactly once per run; `ESC[?2004h` = 0 (no bracketed paste yet) (measured 2026-09-20 with `LC_ALL=C /usr/bin/grep -a -o -F`).

## 1. Screen readers

### 1.1 What Ink 7.1.1 does in screen-reader mode (primary: installed source)

- Switch: `this.isScreenReaderEnabled = options.isScreenReaderEnabled ?? process.env['INK_SCREEN_READER'] === 'true';` (`node_modules/ink/build/ink.js:185-187`). Readme: "To enable it, you can either pass the `isScreenReaderEnabled` option to the `render` function or set the `INK_SCREEN_READER` environment variable to `true`." (`node_modules/ink/readme.md` §Screen Reader Support).
- Throttling is disabled: `const unthrottled = options.debug || this.isScreenReaderEnabled;` → `this.renderThrottleMs = unthrottled ? 0 : renderThrottleMs;` and `this.throttledLog = unthrottled ? this.log : throttle(...)` (`ink.js:193-227`).
- Rendering path (`ink.js:371-421`): the tree is rendered by `renderNodeToScreenReaderOutput` (text nodes squashed, boxes joined with `' '` for `row` and `'\n'` for `column`, `aria-role`/`aria-state` prefixed as `(checked) checkbox: …`), then `wrapAnsi(output, terminalWidth, { trim: false, hard: true })`; each change writes `eraseLines(this.lastOutputHeight) + wrappedOutput`; new `<Static>` items are written before the dynamic region as `erase + staticOutput`. **The log-update path (and therefore `cliCursor.hide`) is not used**, so the cursor stays visible.
- `<Text aria-label>` replaces children, `aria-hidden` drops the node: `const childrenOrAriaLabel = isScreenReaderEnabled && ariaLabel ? ariaLabel : children; … if (isScreenReaderEnabled && ariaHidden) return null;` (`components/Text.js:12,45`); same for `<Box aria-hidden>` (`components/Box.js:10`). Hook: `useIsScreenReaderEnabled()` (`hooks/use-is-screen-reader-enabled.js`). Supported `aria-role` values include `progressbar`, `textbox`, `timer`, `list`, `listitem`, `menu`, `menuitem`, `button`, `checkbox`; `aria-state` includes `busy`, `selected`, `disabled`, `expanded` (readme).
- **Measured (2026-09-20, `/tmp/jev-tui-bench/sr-mode.mjs`)**: a `<Static>` transcript plus an `aria-hidden` spinner line and an `aria-label`led status line, 20 status updates + 4 static appends against a fake 80×24 TTY. Normal mode: 74 writes, 1,607 bytes, 60× `ESC[2K`, 40× cursor-up, 1× `ESC[?25l`, 21 sync pairs, spinner text present. Screen-reader mode: 78 writes, 1,392 bytes, 20× `ESC[2K`, **0 cursor-up, 0 cursor-hide**, 26 sync pairs, spinner text absent, `aria-label` text ("status: step N of 40, stage judge") emitted. Conclusion: Ink's mode removes multi-line repaints and hidden cursors but *still erases and rewrites the dynamic region on every state change* — so the app must keep that region small and change it rarely, or a screen reader re-announces churn.

### 1.3 Codex (Rust/ratatui) — the richest evidence of what breaks for screen-reader users

- Issue #11823 "CLI is unuseable with a screen reader while text is streaming due to repeated/partial announcements of incoming text" (opened 2026-02-14, NVDA on Windows): the TUI "frequently rewrit[es] terminal lines" for "status animations, elapsed timers, and streaming execution output"; "These rewrites get treated as fresh content changes, so even minor edits to an existing line are announced again as full/partial new output."; wanted: "stable, coherent append-oriented updates, not repeated announcements caused by visual-only redraw churn or in-place line rewrites." (https://github.com/openai/codex/issues/11823, 2026-09-20).
- Issue #44728 "macOS VoiceOver regression in 0.154.0: repeated output fragments; disabling animations restores usability" (2026-09-11): VoiceOver "continually announcing fragments of terminal output"; `codex -c tui.animations=false` "restored full functionality" (https://github.com/openai/codex/issues/44728, 2026-09-20).
- Issue #46111 "TUI status timer stops updating when `tui.animations = false`" (2026-09-17): with animations off the elapsed counter "freezes and fails to update"; proposed fix: repaint "once per second while a timer displays" or event-driven (https://github.com/openai/codex/issues/46111, 2026-09-20). **Pitfall:** do not couple functional refreshes (wall clock, step counter) to the animation timer.
- PR #20564 "Enforce `animations = false` for screen readers" (merged 2026-05-01): "animated TUI affordances can be noisy for screen-reader users"; centralises motion in `tui/src/motion.rs`; "Omit the live status-row spinner when animations are disabled"; adds "a source-scan regression test that rejects direct `spinner(...)` or `shimmer_spans(...)` usage outside the central module." (https://github.com/openai/codex/pull/20564, 2026-09-20). `motion.rs` doc: "Centralized motion primitives for the TUI. Callers choose an explicit reduced-motion fallback here instead of reaching directly for time-varying spinner or shimmer helpers."; `activity_indicator(start_time, motion_mode, reduced_motion_indicator)` returns `None` (Hidden) or a dimmed `•` (StaticBullet); `shimmer_text` degrades to plain text (https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/motion.rs, 2026-09-20).
- PR #46040 "Default TUI animations off when a screen reader is detected" (merged 2026-09-16): probes "at startup on macOS, Windows, and Linux, with a 450 ms timeout", writes `tui.animations = false` and `tui.screen_reader_detection_done`, "Allow explicit animation preferences to override the screen-reader default on reload." (https://github.com/openai/codex/pull/46040). Detection code: `const DETECTION_TIMEOUT: Duration = Duration::from_millis(450);` macOS `NSWorkspace::sharedWorkspace().isVoiceOverEnabled()`, Windows `SystemParametersInfoW(SPI_GETSCREENREADER, …)` plus `narrator_running()`, Linux AT-SPI DBus `ScreenReaderEnabled`/`IsEnabled` and `org.gnome.Orca.Service` presence; "Presence of the completion marker skips detection, including when its value is false." (https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/screen_reader.rs, 2026-09-20).
- Config: `tui.animations` "Enable terminal animations (welcome screen, shimmer, spinner)" default `true`; `tui.alternate_screen` `auto | always | never` "auto skips it in Zellij to preserve scrollback"; `tui.status_line` "`null` disables the status line." (https://learn.chatgpt.com/docs/config-file/config-reference, 2026-09-20). CLI: `/// Disable alternate screen mode /// Runs the TUI in inline mode, preserving terminal scrollback history. #[arg(long = "no-alt-screen", default_value_t = false)] pub no_alt_screen: bool,` (https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/cli.rs, 2026-09-20).

### 1.4 Claude Code's screen-reader mode (documentation; the most complete spec of user needs found)

Source: https://code.claude.com/docs/en/accessibility (2026-09-20). Verbatim points that map directly onto JevCode:
- Enable: `claude --ax-screen-reader`, env `CLAUDE_AX_SCREEN_READER=1`, setting `"axScreenReader": true`; precedence "the `--ax-screen-reader` flag over the `CLAUDE_AX_SCREEN_READER` environment variable, and the variable over the `axScreenReader` setting"; `CLAUDE_AX_SCREEN_READER=0` "keeps the mode off even when the setting is `true`"; first line confirms: `[Screen Reader Mode: on via flag]`.
- Output: "No box-drawing characters for the interface chrome · No color-only cues · No redraws of content that hasn't changed. Progress spinners render as static text · Tables … read as `Header: value` sentences"; "leaves everything it prints in your terminal's scrollback".
- Timing: waits 3 s after the confirmation line (`CLAUDE_AX_STARTUP_QUIET_MS`); "Before Claude Code writes a new or changed line … it moves the cursor to the start of the line and waits 50 milliseconds" (`CLAUDE_AX_PREPARK_MS`) so the reader "reads the line from its first character".
- Labels every message: `you:`, `claude:`, `thinking:`, `tool:`, `tool error:`, `error:`, `warning:`, `Permission Required:`, `Cost:` — "also searchable, so you can jump between sections".
- Menus become numbered lists with an `Enter selection` prompt; yes/no prompts take typed `y`/`n` + Enter; deletions announce the deleted text; mode changes are announced "once and doesn't repeat it on later redraws"; terminal bell when a reply finishes, a prompt needs an answer, or a tool ran > 5 s; OSC 133 prompt marks for jump-to-previous-prompt (iTerm2 Cmd+Shift+Up; "macOS Terminal doesn't act on the markers").
- Related settings: `prefersReducedMotion` "Reduced or no spinners, shimmer, and other animations when `true`"; `theme` with "colorblind-friendly `dark-daltonized` and `light-daltonized` themes"; `CLAUDE_CODE_ACCESSIBILITY=1` keeps "a terminal cursor that stays visible for screen magnifiers such as macOS Zoom".
- Limitation stated: "Screen reader mode doesn't turn on automatically when a screen reader is running."

Community summary (secondary): "Unlike the web, there is no standardized 'accessibility tree' for terminal applications." and CLIs should give "clear, structured, and linear output" (https://afixt.com/accessible-by-design-improving-command-line-interfaces-for-all-users/, WebSearch snippet, 2026-09-20).

### 1.5 Design for JevCode `--screen-reader`

1. Switch: `--screen-reader` flag → `JEVCODE_SCREEN_READER=1|0` → config `ui.screenReader` (flag > env > file, `0` wins over file, mirroring Claude Code). Pass `isScreenReaderEnabled` explicitly to `render()` and also honour `INK_SCREEN_READER=true` (Ink default). Do **not** auto-probe assistive tech (Codex's 450 ms probe would cost up to 450 ms of the 300 ms first-frame budget; Claude Code also declines to auto-detect). Print `[screen reader mode: on via flag|env|config]` as the first `<Static>` line.
2. In this mode the dynamic region holds only the composer line and a *one-line* status that changes only on stage transitions (never on ticks); the spinner is `aria-hidden` (dropped by Ink) and the status text uses `aria-label="status: step 3 of 40, stage judge"`. The live stream region is off; the proposal text arrives as one `<Static>` item at `proposal` (it already does). Wall time is shown only in the committed `outcome`/`run:end` lines — Codex #46111 shows a frozen timer is worse than none.
3. Every `<Static>` line keeps the existing `formatTranscriptItem` shape (`[step 3] intent=edit …`), which already gives a searchable label per kind; add the `you:`-style prefixes for composer turns (`you:`, `steer:`) so users can jump by search. Same lines go to `transcript.log` and `--plain` — parity stays exact.
4. Review prompts: keep `[y] approve  [n] decline` but also accept `y`/`n` + Enter typed into the composer; in screen-reader mode render the request as numbered lines (`1. approve  2. decline`) followed by `Enter selection (1-2):`, as Claude Code does. Ring `\x07` (BEL) when a review is pending or the run ends, screen-reader mode only (opt-in elsewhere, cf. `preferredNotifChannel: "terminal_bell"`).
5. No box borders anywhere (`borderStyle` never used) — already true; keep the rule line (`─` × columns) out of screen-reader mode (it is read as "box drawings light horizontal" × 120).
6. Optional refinement to evaluate later: Claude Code's 50 ms "pre-park" before rewriting a changed line. Ink's SR path rewrites with `eraseLines + wrappedOutput` in one write; a pre-park would need a custom `stdout` wrapper that splits writes — leave as an open question.

## 2. Reduced motion (spinner/animation off)

- WCAG 2.2.2 Pause, Stop, Hide: "For any moving, blinking or scrolling information that (1) starts automatically, (2) lasts more than five seconds, and (3) is presented in parallel with other content, there is a mechanism for the user to pause, stop, or hide it"; moving content "can also cause problems for screen readers" (https://www.w3.org/WAI/WCAG21/Understanding/pause-stop-hide.html, 2026-09-20). A braille spinner at 8 fps for a 30-minute run is exactly this.
- Prior art: Codex `tui.animations=false` (+ pitfalls above), Claude Code `prefersReducedMotion`, Gemini `ui.loadingPhrases: "off"` (default off).
- JevCode: `--no-animation` flag / `JEVCODE_REDUCED_MOTION=1` / `ui.reducedMotion`; implied by `--screen-reader`. Implementation: `useSpinner(active && !reducedMotion)`; status line shows a static `•` or the stage word alone; **keep a 1 Hz tick for wall time** so the counter never freezes (Codex #46111). Copy Codex's guard: a unit test that greps `src/tui/**` for `setInterval(` outside `StatusLine.tsx`/`useSpinner` so nobody adds an unbounded animation (PR #20564's "source-scan regression test").
- Ink-side: even with no spinner, the 50 ms live coalescer redraws while streaming; under reduced motion raise `LIVE_FLUSH_MS` to 250 ms (4 fps) and truncate to the last line only. This is a knob, not a mode.

## 3. Colour: NO_COLOR, colour-blind safety, background detection

### 3.1 Standards and Node facts
- NO_COLOR: "Command-line software which adds ANSI color to its output by default should check for a `NO_COLOR` environment variable that, when present and not an empty string (regardless of its value), prevents the addition of ANSI color."; configuration and flags "should override the `NO_COLOR` environment variable" (https://no-color.org/, 2026-09-20).
- Node 22 `tty.WriteStream.getColorDepth([env])` returns 1/4/8/24; "2 colors: `FORCE_COLOR = 0` (Disables colors) · 16 colors: `FORCE_COLOR = 1` · 256 colors: `FORCE_COLOR = 2` · 16,777,216 colors: `FORCE_COLOR = 3`"; "Disabling color support is also possible by using the `NO_COLOR` and `NODE_DISABLE_COLORS` environment variables."; `hasColors([count][, env])` "Returns `true` if the `writeStream` supports at least as many colors as provided in `count`." (https://nodejs.org/docs/latest-v22.x/api/tty.html, 2026-09-20). **Measured:** when stdout is a pipe, `process.stdout.getColorDepth` and `.hasColors` are `undefined` (plain `Writable`, not `tty.WriteStream`) — guard with `typeof stdout.hasColors === 'function'`.
- `util.styleText` **measured** (Node 22.23.2, stdout a pipe): default → `"x"` (no colour); `NO_COLOR=1` + `{ validateStream: false }` → `"\u001b[31mx\u001b[39m"` (**NO_COLOR is ignored when stream validation is off**); `NO_COLOR=1` default → `"x"`; `FORCE_COLOR=1` in a pipe → coloured; `FORCE_COLOR=1 NO_COLOR=1` → coloured with warning "The 'NO_COLOR' env is ignored due to the 'FORCE_COLOR' env being set." Research 08 records styleText stable since v22.13.0.
- Ink colours through chalk (`components/Text.js` uses `chalk.dim/bold/...` and `colorize`); chalk's level comes from `supports-color`, which honours `NO_COLOR`/`FORCE_COLOR` — **UNVERIFIED** against the installed chalk source (not read); the perf pty transcript shows `\u001b[2m…\u001b[22m` (dim) with `TERM=xterm-256color`, so colour is on by default in a pty. Test both `NO_COLOR=1` and `FORCE_COLOR=0` in a pty and assert zero SGR sequences except the ones Ink needs for erase/cursor.

### 3.2 Never colour-only
- WCAG 1.4.1: "Color is not used as the only visual means of conveying information, indicating an action, prompting a response, or distinguishing a visual element."; lightness-only distinctions count only at "a contrast ratio of 3:1 or greater" (https://www.w3.org/WAI/WCAG21/Understanding/use-of-color.html, 2026-09-20).
- The current decisions pane already pairs colour with a word: `[review]`, `[block]`, `[ok]`, `[overridden]`, `derived` (asserted in `test/unit/tui/app.test.tsx`). Keep this invariant for every new pane: verdict/level → bracketed word or glyph (`✗ blocked`, `? review`, `✓ ok`), with an `aria-label` where the glyph is decorative.
- Palette: prefer the 16 ANSI colours (they follow the user's theme, and daltonized themes remap them). Red/green is the failing pair for ~8% of Caucasian, 5% of Asian, 4% of African males ("One in twelve Caucasian (8%), one in 20 Asian (5%), and one in 25 African (4%) males are so-called 'red-green' colorblind"; "do not use the combination of red and green. Use magenta (purple) and green instead." https://jfly.uni-koeln.de/color/, 2026-09-20). The page gives vermilion `#FF2000`-ish guidance but not a full 8-colour RGB table in the fetched text — the exact Okabe–Ito RGB values are **UNVERIFIED** here; not needed if we stay on ANSI 16. Claude Code ships `dark-daltonized`/`light-daltonized` themes (§1.4) — JevCode can offer `--theme daltonized` that swaps red→magenta/vermilion and green→sky-blue at the 16-colour level.

### 3.3 Light/dark background detection
- OSC 11 query: xterm ctlseqs "OSC Ps ; Pt ST … Ps = 1 1 → Change VT100 text background color"; "if Pt is a '?', the control sequence elicits a response which consists of the control sequence which would set the corresponding value", response uses `rgb:RRRR/GGGG/BBBB` (https://invisible-island.net/xterm/ctlseqs/ctlseqs.html, 2026-09-20). Query `OSC 11 ; ? ST`, reply `OSC 11 ; rgb:RRRR/GGGG/BBBB ST`; supported by Alacritty, contour, foot, Ghostty, iTerm2, Kitty, Konsole, mintty, Rio, rxvt-unicode, st, VTE, WezTerm, Windows Terminal, xterm, tmux ≥ 2.6, GNU screen ≥ 4.7.0, VS Code xterm.js 4.16.0; PuTTY does not (https://vtdn.dev/docs/osc/osc11/, 2026-09-20). **Apple Terminal is not in that table → UNVERIFIED** (WebSearch found Terminal.app answers OSC 12/17/19 but nothing explicit for 11; cannot be tested from this non-TTY session). iTerm2 additionally documents `OSC 4 ; -2 ; ? ST` → `OSC 4 ; -2 ; rgb : [red] / [green] / [blue] ST` for the default background (https://iterm2.com/documentation-escape-codes.html, 2026-09-20). Guidance: "Set a short timeout (100–200ms). Terminals that don't support a query won't respond — don't block on it forever." (https://terminfo.dev/fundamentals/color-detection, 2026-09-20).
- `COLORFGBG`: set by rxvt-unicode "to a string of the form "fg;bg" or "fg;xpm;bg"" (https://man.archlinux.org/man/urxvt.1.en, 2026-09-20). Vim: "'dark' is used when 'term' is 'linux', 'screen.linux', 'cygwin' or 'putty', or $COLORFGBG suggests a dark background. Otherwise the default is 'light'." and "When the |t_RB| option is set, Vim will use it to request the background color from the terminal." (https://raw.githubusercontent.com/vim/vim/master/runtime/doc/options.txt, 2026-09-20). **Measured:** `COLORFGBG`, `TERM_PROGRAM`, `COLORTERM` are all unset in this tool's environment; iTerm2/Terminal.app defaults for `COLORFGBG` are **UNVERIFIED** (not testable here; Terminal.app/iTerm2 set `TERM_PROGRAM=Apple_Terminal`/`iTerm.app` per common knowledge — treat as heuristic only).
- **Hazard specific to Ink:** an OSC 11 reply arrives on stdin while Ink's input parser owns stdin; Ink only recognises kitty `CSI ? … u` replies (`matchKittyQueryResponse` in `ink.js`), so `ESC ] 11 ; rgb:… ESC \` would be delivered to `useInput` as garbage keys (and `use-input.js` strips a leading ESC and passes the rest as `input`). A probe therefore has to run *before* `render()` (violating "first frame from argv only, zero reads") or through a custom stdin wrapper. **Decision: no background probe at launch.** Use ANSI 16 defaults, no explicit background colours, `dimColor` for de-emphasis; revisit as an opt-in `/theme detect` command after the first frame (see OPEN QUESTIONS).

## 4. Terminal size, degradation, resize

- Ink size source: `getWindowSize(stdout)` → `stdout.columns/rows` if both truthy, else `terminal-size` (which tries `process.stdout`, `process.stderr`, `COLUMNS`/`LINES`, `/dev/tty` on darwin, then spawns `tput cols`/`tput lines` with a 500 ms timeout, and finally 80×24) (`node_modules/ink/build/utils.js`, `node_modules/terminal-size/index.js`, 2026-09-20). **Measured:** a pty spawned by `expect` starts at `size=0x0` until `stty` sets it (`/tmp/jev-tui-bench/resize.exp`), which is why `tui-run.exp` sets `stty_init "rows 40 cols 120"` and `first-frame.ts` prefixes `stty rows 40 cols 120;`. Any pty test must set geometry first or Ink measures the *host* terminal via `/dev/tty`.
- Ink resize handler: on `resize`, if `currentWidth < this.lastTerminalWidth` Ink does `this.log.clear()` (erase-lines, **not** `ESC[2J`) then re-renders (`ink.js` `resized`). The App's `useTerminalSize` re-derives `computeLayout(rows, …)` so the dynamic region shrinks to `rows − 2` on the next frame (local read).
- Prior art: Gemini `export function isNarrowWidth(width: number): boolean { return width < 80; }` (https://raw.githubusercontent.com/google-gemini/gemini-cli/main/packages/cli/src/ui/utils/isNarrowWidth.ts, 2026-09-20) and no "terminal too small" check in `interactiveCli.tsx` (fetched, 2026-09-20). - JevCode rule: `MIN_COLUMNS = 40`, `MIN_ROWS = 8`. Below that the dynamic region degrades to two lines: `terminal too small (Wx H); need 40x8` + composer, the transcript keeps flowing into `<Static>` (never lost), and nothing is clipped mid-grapheme (truncate by width, §6). Between 40 and 80 columns: hide probabilities/confidence in the decisions rows, keep verdict words; composer wraps. `computeLayout` already allocates in priority order (status, rule, live, confirm header, preview, decisions); add the composer *before* the live region in that order.

## 5. High-latency terminals and render throttling

- Ink: `maxFps` default 30 → `renderThrottleMs = Math.max(1, Math.ceil(1000 / maxFps))` = 34 ms; `incrementalRendering` "only updates changed lines instead of redrawing the entire output" (readme; `log-update.js` `createIncremental` writes only lines that differ, with `cursorNextLine` skips). Synchronized output: `bsu = '\u001B[?2026h'`, `esu = '\u001B[?2026l'`, emitted when `stream.isTTY && (interactive ?? !isInCi)` (`write-synchronized.js`). Spec: begin `CSI ? 2026 h`, end `CSI ? 2026 l`, query `CSI ? 2026 $ p` → `CSI ? 2026 ; Ps $ y`; purpose: keep showing the previous frame "while processing incoming text and sequences" so there is no tearing; "So far there is no real consensus if and if so how long a timeout should be." (https://gist.github.com/christianparpart/d8a62cc1ab659194337d73e399004036, 2026-09-20).
- Gemini enables `incrementalRendering` only inside the alternate buffer (§1.2) and logs frames slower than 200 ms. Gemini issue "Severe screen flickering in interactive mode over SSH · #11305" exists (title from WebSearch, 2026-09-20; body **UNVERIFIED**).
- Measured frame cost today: a 120-column frame under `script` is ~1.4 KB (pty log bytes ÷ frames, e.g. `01-fix/tui-pty.log` 807,646 B / 593 frames ≈ 1.36 KB); at 20 fps that is ~27 KB/s — fine on LAN, noticeable on a 3G-class link.
- JevCode: keep Ink's 30 fps cap and the 50 ms coalescer; add `--fps <n>` (env `JEVCODE_FPS`) and automatically choose 10 fps when `SSH_CONNECTION`/`SSH_TTY` is set (a heuristic; document it). Do **not** switch to `incrementalRendering` while the transcript is inline: Gemini restricts it to the alt buffer and the readme warns "may cause rendering artifacts". Never clear the terminal (perf gate exists).

## 6. Memory bounds for very long transcripts

- `<Static>` only renders the *new* items (`itemsToRender = items.slice(index)` then `setIndex(items.length)` in a layout effect), so React does not keep fibers for old rows (`components/Static.js`). But Ink 7.1.1 keeps `this.fullStaticOutput += staticOutput` for every frame with static output (`ink.js` `onRender`, non-debug path) and replays it on the clear-terminal path: `this.options.stdout.write(ansiEscapes.clearTerminal + this.fullStaticOutput + outputToRender)` (`ink.js:768`). PR #1005 "Stop replaying `<Static>` output on full-clear frames" (author costajohnt) would make `fullStaticOutput` "only accumulated in debug mode" — **still open, not merged** as of 2026-09-20 (https://github.com/vadimdemedes/ink/pull/1005). So with 7.1.1 the whole transcript text lives twice (our `items` array and Ink's string).
- **Measured (`/tmp/jev-tui-bench/static-mem.mjs`, 2026-09-20, fake 120×40 TTY, batches of 50 items):** 5,000 items (712,780 chars) → heap +8.6 MB, 0.7 MB written, 437 ms; 20,000 items (2.88 MB) → heap +30.4 MB, 2.8 MB written, 1.42 s. In **debug mode** (what ink-testing-library uses) 5,000 items wrote **69 MB** to the fake stdout because every frame rewrites `fullStaticOutput + output` — the frames array of ink-testing-library retains all of it. A 10-hour chat session at one item per 5 s is 7,200 items → ~12 MB; acceptable, but tests must not push thousands of items through ink-testing-library.
- Bounds already in place: per-item caps (`TRANSCRIPT_TEXT_MAX 600`, detail 60 lines/6,000 chars), live buffer 64 KB, `BUS_REPLAY_MAX 10_000`. Add: (a) a `UiState.items` soft cap of 20,000 with a `/compact` (or automatic) **Static remount**: change the `<Static key>` so Ink's `handleStaticChange` resets `fullStaticOutput = ''` (`ink.js` `onStaticChange`), as Gemini does with `historyRemountKey` (research 05 §1.3), and drop the old array — older rows remain in terminal scrollback; (b) `detail` bodies for `proposal` items are the largest rows — keep the 6,000-char cap for chat mode too.

## 7. Unicode input, IME composition, cursor placement, widths

- Grapheme clusters: "it can be useful to speak of a *user-perceived character*"; "An **extended grapheme cluster** is the same as a legacy grapheme cluster, with the addition of some other characters."; they are units "for processes such as … the implementation of text selection, arrow key movement, forward deletion, and so forth" (https://unicode.org/reports/tr29/, 2026-09-20).
- Node 22 has `Intl.Segmenter` (**measured**: `[...new Intl.Segmenter(undefined,{granularity:'grapheme'}).segment('é👨‍👩‍👧🇯🇵')]` → segment lengths `[2, 8, 4]` UTF-16 units; 200,000 mixed graphemes (432,177 code units) segmented in 50.2 ms = **251 ns/grapheme**; constructor 5.6 ms once; `Array.from` code-point split 1.8 ms for the same string). A composer line is < 10 K graphemes, so re-segmenting the whole buffer per keystroke costs < 3 ms — acceptable, but cache segments per line.
- Width: Ink measures with `string-width` 8.2.2, which itself uses `new Intl.Segmenter()` and rules "RGI emoji clusters (\p{RGI_Emoji}) are double-width", "Skip non-printing clusters (Default_Ignorable, Control, pure nonspacing/enclosing Mark…). Tabs are ignored by design.", East-Asian-Width for the rest (`node_modules/string-width/index.js`, 2026-09-20). **Measured** `string-width('👨‍👩‍👧日本é')` = 7; module import 17.3 ms (already paid inside Ink's first frame). `string-width` is *not* a JevCode dependency (transitive only); importing it directly is fragile under the one-package rule — write `tui/text/width.ts` with the same three rules (`/^\p{RGI_Emoji}$/v`, `\p{Nonspacing_Mark}`/`\p{Format}` zero, an East-Asian-Wide/Fullwidth range table) and unit-test it against string-width for a fixture corpus.
- IME: Ink `useCursor()`: "Setting a cursor position makes the cursor visible at the specified coordinates (relative to the Ink output origin). This is useful for IME (Input Method Editor) support, where the composing character is displayed at the cursor location." (`hooks/use-cursor.js`, 2026-09-20). The composer must call `setCursorPosition({x: widthOfPrefix, y: row})` from the *width* of graphemes before the cursor, not the string index, or Hangul/CJK/emoji composition popups land in the wrong cell.
- Paste: `usePaste` "Bracketed paste mode (`\x1b[?2004h`) is automatically enabled while the hook is active, so pasted text arrives as a single string"; "paste content is never forwarded to `useInput` handlers when `usePaste` is active" (`hooks/use-paste.js`); Ink's `App.js` emits `'paste'` only if a listener exists, else forwards the text as input. xterm: `CSI ? 2 0 0 4 h` bracketed paste; pastes are wrapped `ESC [ 2 0 0 ~` … `ESC [ 2 0 1 ~` (ctlseqs). Bracketed paste also protects against `\r` in pasted multi-line text submitting early (Ink delivers the paste whole).
- Key protocol: Ink's parser table (`parse-keypress.js`) covers xterm/rxvt/putty sequences (`'[A': 'up'`, `'[3~': 'delete'`, `'[Z': 'tab'` (shift-tab), `'[5~': 'pageup'`…), meta as `ESC + letter`, and kitty `CSI u` when `kittyKeyboard: { mode: 'auto' }` is enabled (readme: "Detect terminal support using a heuristic precheck (known terminals like kitty, WezTerm, Ghostty) followed by a protocol query confirmation (`CSI ? u`)"). Kitty mode disambiguates Shift+Enter/Ctrl+Enter, but the auto probe writes to the terminal at start-up and waits on a reply — leave **off** for v1 (first-frame budget), revisit when a "newline vs submit" binding is needed (Codex's `set_modes()` enables enhancement flags "so modifiers for keys like Enter are disambiguated", https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/tui.rs, 2026-09-20).

## 9. Copy/paste friendliness and OSC 52

- Selection works over `<Static>` because rows are plain lines in scrollback; keep it that way: no borders, no `paddingLeft` gutters that insert spaces into copied code, and code/diff bodies printed verbatim (the 6,000-char cap applies). Claude Code's screen-reader mode lists "No box-drawing characters" as a feature (§1.4); Codex's `--no-alt-screen` exists to "preserv[e] terminal scrollback history" (§1.3). REJECT the alternate screen for the chat mode as well (Ink readme: "The terminal's scrollback buffer is not available while in the alternate screen").
- OSC 52: "OSC Ps ; Pc ; Pd ST … Ps = 5 2 → Manipulate Selection Data … Pc denotes the selection (c, p, q, s, or 0 through 7) … Pd is base64 encoded data" (ctlseqs, 2026-09-20). Support: Apple Terminal **No**; iTerm2 Yes; Kitty ≥ 0.36.2; WezTerm; Alacritty ≥ 0.2.1; Windows Terminal ≥ 1.2.2022.0; VS Code ≥ 1.93; tmux ≥ 2.5; xterm/st opt-in (https://can-i-use-terminal.github.io/features/osc52copy.html, 2026-09-20). tmux: `set-clipboard on` "both makes tmux set the clipboard for the outside terminal, and allows applications inside tmux to set tmux's clipboard"; "If a command can write text to a tmux pane, it can set the clipboard."; iTerm2 "requires enabling in preferences"; VTE terminals do not support it (https://github.com/tmux/tmux/wiki/Clipboard, 2026-09-20).
- JevCode `/copy [last|proposal|diff]`: try a native tool first (`pbcopy` on darwin, `wl-copy`, `xclip -selection clipboard`, `xsel --clipboard --input`) as opencode does ("prefers Wayland clipboard when available", "uses osascript on macOS", "falls back through X11 clipboard commands", https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/tui/test/clipboard.test.ts, 2026-09-20); fall back to OSC 52 (`\x1b]52;c;<base64>\x07`) only with `--osc52` (`ui.osc52: true`), never automatically — the sequence is silently dropped by Terminal.app and is a clipboard-write vector if ever fed with untrusted content. `sanitizeStream` already guarantees command output cannot emit OSC 52 itself.

## 10. Crash recovery: terminal restore and checkpoint

- Ink registers `signalExit(this.unmount, { alwaysLast: false })` at construction; `unmount()` unmounts the React tree (so `useInput`'s cleanup calls `setRawMode(false)` and bracketed paste count drops to 0 → `'\u001B[?2004l'`), pops kitty (`'\u001B[<u'` if enabled), leaves the alt screen if used, and `this.log.done()` shows the cursor (`ink.js` `unmount`/`finishUnmount`, `App.js:136,272`). The perf transcript ends with `\u001b[?25h` (three times — Ink and cli-cursor both restore).
- Node: "'SIGTERM' and 'SIGINT' have default handlers on non-Windows platforms that reset the terminal mode before exiting with code `128 + signal number`. If one of these signals has a listener installed, its default behavior will be removed" (https://nodejs.org/docs/latest-v22.x/api/process.html, 2026-09-20). JevCode installs both listeners (`main.tsx`), so *our* shutdown must restore the terminal — today it does through `renderer.unmount()` (bounded by `UNMOUNT_TIMEOUT_MS = 2000`) and the checkpoint sequence in DESIGN §11.
- Gap: `fatalExit` (`uncaughtException`/`unhandledRejection`) calls `process.exit(err.exitCode)` without awaiting `renderer.unmount()`; signal-exit's synchronous `unmount` runs, but if Ink itself threw mid-render the tree may be inconsistent. Add a belt-and-braces `restoreTerminal(stdout, stdin)` in `fatalExit`: `stdin.isTTY && stdin.setRawMode(false)`; write `'\x1b[?2004l\x1b[?25h'` (+ `'\x1b[<u'` if kitty ever enabled); no `ESC c` (RIS) — it would clear the screen and violate the zero-clear rule. Codex does the same in `set_panic_hook`: `let _ = restore_after_exit(); // ignore any errors as we are already failing`, and `restore_common()` runs `disable_raw_mode()`, `DisableBracketedPaste`, `SetCursorStyle::DefaultUserShape`, `crossterm::cursor::Show` (https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/tui.rs, 2026-09-20).
- Checkpoint on crash is already the engine's job (§11: final `state.json` written synchronously as a last resort). For the chat mode add the *composer draft* to the checkpoint-adjacent `ui.json` (not `state.json`) so `--resume` can restore an unsent prompt; never store keystroke history.

### 10.1 Ctrl-Z / fg (measured protocol)
- In raw mode the terminal sends no `SIGTSTP`; Ctrl-Z arrives as byte `0x1a` (**measured** with `expect`: `BYTES 1a`). Node's readline docs describe the cooked-mode behaviour: "The `'SIGTSTP'` event is emitted when the `input` stream receives a Ctrl+Z input … If there are no `'SIGTSTP'` event listeners registered … the Node.js process will be sent to the background."; "The `'SIGCONT'` event is emitted when a Node.js process previously moved into the background using Ctrl+Z (i.e. `SIGTSTP`) is then brought back to the foreground using `fg(1p)`"; both "not supported on Windows" (https://nodejs.org/docs/latest-v22.x/api/readline.html, 2026-09-20).
- Working sequence (**measured** under an interactive `bash --noprofile --norc -i` in an expect pty, `/tmp/jev-tui-bench/ctrlz-fg.exp`): on `0x1a` → `stdin.setRawMode(false)` → `process.kill(process.pid, 'SIGTSTP')` (no `SIGTSTP` listener installed!) → `ps -o stat=` shows `T`, bash prints `[1]+  Stopped  node …` → `fg` → `process.on('SIGCONT')` fires → `setRawMode(true)` → `isRaw` true and the next `0x1a` arrives as a byte again. Codex documents the shell race to expect: "A shell may restore the job's saved termios after the process receives `SIGCONT`. When that races with [`set_modes`], crossterm still believes raw mode is enabled even though the terminal has returned to canonical, echoing mode." (`reapply_raw_mode_after_resume()`, tui.rs, 2026-09-20) — so re-apply raw mode on `SIGCONT` *and* on the next stdin data, and force a full redraw (Ink: `instance.clear()` then re-render, or use `useApp().suspendTerminal()` which "restores the terminal modes the child expects (raw mode off, cursor visible, bracketed paste off, alternate screen exited, kitty keyboard protocol off) … When the suspension ends, Ink reapplies its own terminal state and repaints from scratch." (readme §suspendTerminal)). The cleanest implementation: `const s = await suspendTerminal(); process.once('SIGCONT', () => void s.resume()); process.kill(process.pid, 'SIGTSTP');`.
- **Test-harness caveat (measured):** when `expect` spawns node *directly* (node is a session leader whose parent is in another session), a self-sent `SIGTSTP` did **not** stop the process (`ps` state `Ss+`, and the flow continued), whereas `SIGSTOP` did (`Ts+`). Under a job-control shell (`bash -i`) `SIGTSTP` stopped it (`T`). The likely reason is the orphaned-process-group rule for stop signals; the POSIX sentence was not located (setpgid(2) defines "An orphaned process group is one in which the parent of every member of process group is either itself also a member of the process group or is a member of a process group in a different session." but does not state the discard rule — https://man7.org/linux/man-pages/man2/setpgid.2.html, 2026-09-20; **UNVERIFIED** attribution). Practical rule: pty tests for Ctrl-Z must spawn through an interactive shell and drive `fg`, as `ctrlz-fg.exp` does.

### 12.3 Snapshot policy (and how to avoid brittleness)
- Snapshot only (a) `renderToString` output of leaf components at fixed widths 40/80/120 and (b) the *dynamic region* of `lastFrame()` (everything from the last rule line), never whole frames with `<Static>` history.
- Normalise before snapshotting: strip SGR/CSI with `util.stripVTControlCharacters` (Node built-in), replace spinner glyphs (`[⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏]` → `⠿`), durations (`\d+m \d+s` → `<t>`), run ids (`RUN_ID_RE`) and money to fixed tokens via a shared `expect.addSnapshotSerializer`. Fixed `Stdout.columns` (100 in ink-testing-library; pass explicit stubs for others).
- Prefer `toMatchInlineSnapshot()` for ≤ 6-line regions (reviewable in the diff), file snapshots under `test/unit/tui/__snapshots__/` for the rest; CI fails on missing/obsolete snapshots automatically (vitest CI rule above). Wrapping/width bugs are what snapshots catch; behaviour goes into explicit assertions (`toContain('[review]')`).
- Gemini's SVG snapshots are for visual review of colours; skip (colour is asserted by the presence of SGR codes in a dedicated test, not by images).

### 12.4 Key-sequence fuzzing for the text buffer (tiny generator, no deps)
- PRNG: mulberry32 (`a = a + 0x6D2B79F5 | 0; t = Math.imul(a ^ a >>> 15, 1 | a); t = t + Math.imul(t ^ t >>> 7, 61 | t) ^ t; return ((t ^ t >>> 14) >>> 0) / 4294967296`) seeded per test and printed on failure so the case replays (`/tmp/jev-tui-bench/grapheme.mjs` used it, 2026-09-20).
- Alphabet of operations: `insert(g)` for g drawn from a pool `['a','é','é','👨‍👩‍👧','🇯🇵','日','ｚ','한','👍🏽','\n',' ']`, `paste(text with \r\n)`, `left/right/home/end`, `wordLeft/wordRight` (`ESC b`/`ESC f`), `backspace`, `delete`, `killWord` (`Ctrl-W`), `killToEnd` (`Ctrl-K`), `killToStart` (`Ctrl-U`), `undo/redo`, `historyUp/Down`, and raw *bytes* from `parse-keypress`'s table (`\x1b[A`, `\x1b[3~`, `\x1b[1;5D`, `\x1b[200~…\x1b[201~`, lone `\x1b`) fed through Ink's parser path (via `stdin.write` in an ink-testing-library test) — the last group checks that unknown/incomplete sequences never insert `ESC`-prefixed garbage (Ink strips a leading ESC: "Strip escape prefix from broken/incomplete sequences", `use-input.js`).
- Invariants after every op (model = array of graphemes + cursor index): (1) `cursor ∈ [0, graphemes.length]`; (2) `text === graphemes.join('')` and `[...seg.segment(text)].length === graphemes.length` (Segmenter is the oracle; **measured** 10,000 random moves keep the boundary invariant); (3) no code point in `[\u0000-\u0008\u000b\u000c\u000e-\u001f\u007f-\u009f]` (sanitiser applied to pastes); (4) `insert(g)` then `backspace` is identity; `killWord` then `undo` is identity; (5) `width(renderedLine) ≤ columns` for every wrapped line and the rendered cursor `(x, y)` equals `widthOf(graphemes.slice(0, cursor))` folded by the same wrap; (6) a `paste` is one undo step and one history entry; (7) rendering is a pure function of `(text, cursor, columns)`. Shrink by replaying prefixes of the op list until the failure disappears.
- Property tests are just the same generator with 1,000–5,000 iterations per property under `it.each(seeds)`; budget < 2 s per file.

### 12.5 Event-loop lag, frame counts, zero clears
- Lag: keep the 10 ms `setInterval` probe (`startLagProbe` in `main.tsx`) for continuity, but the canonical API is `perf_hooks.monitorEventLoopDelay({ resolution })` — "Creates an `IntervalHistogram` object that samples and reports the event loop delay over time. The delays will be reported in nanoseconds." with `h.percentile(99)`, `h.max` (https://nodejs.org/docs/latest-v22.x/api/perf_hooks.html, 2026-09-20). Add it behind `--perf-lag-probe` and report both.
- Frames: `render({ onRender })` "Runs the given callback after each render and re-render with render metrics" (`renderTime`) (readme); in a pty capture the number of frames equals the count of `ESC[?2026h` (one synchronized-update pair per frame; **measured** across all live logs `2026h = frames − 2`, e.g. 591 vs 593 status-line occurrences). Assert: during a 500-delta/s mocked stream, frames ≤ 20/s + 1 (coalescer) and, in reduced-motion mode, ≤ 4/s.
- Zero clears: extend `perf/render-lag.ts` (currently `/\x1b\[2J/g` only) to `/\x1b\[[0-9;]*[23]J|\x1bc|\x1b\[\?1049[hl]/g` after the first frame — `ansi-escapes` `clearTerminal` is `` `${eraseScreen}${ESC}3J${ESC}H` `` i.e. `ESC[2J ESC[3J ESC[H` on non-Windows (`node_modules/ansi-escapes/base.js:124-130`); `ESC c` is RIS "Full Reset" and `ESC[3J` "Erase Saved Lines" (ctlseqs). Also assert exactly one `ESC[?25l` per run and a final `ESC[?25h`.

### 12.6 Resize tests (how, measured)
- From `expect`: `set pty $spawn_out(slave,name)` (the man page names it `spawn_out(replica,name)` on this macOS but the `slave` key also works — **measured**: `/dev/ttys005`), then either `exec stty -f $pty rows 20 cols 60` (BSD `stty -f file`: "Open and use the terminal named by file rather than using standard input.", local `man stty`) or expect's built-in `stty rows 50 cols 200 < $pty` ("Other terminals can be accessed by appending "< /dev/tty..." to the command.", local `man expect`). **Measured** child output: `RESIZE=60x20` + `SIGWINCH-signal` for the first; for the second **two** events `RESIZE=60x50` then `RESIZE=200x50` (rows and columns applied as two `TIOCSWINSZ` calls → two SIGWINCH). Tests must wait for the *final* geometry, not count events. Node: "The `'resize'` event is emitted whenever either of the `writeStream.columns` or `writeStream.rows` properties have changed." (tty docs). `kill -WINCH <pid>` alone only re-reads the unchanged size — always change the pty size.
- Assertions after shrinking to rows 12: no `ESC[2J`; dynamic region ≤ 10 rows (the height budget test already covers the layout arithmetic with a stub); after widening back, the composer draft and cursor column are intact; after shrinking *width* Ink emits `log.clear()` erase-lines only.

### 12.7 Ctrl-Z / fg tests
- Shape: `spawn bash --noprofile --norc -i` with `PS1` set, send `node bin/jevcode.js run … --mock\r`, wait for the status sentinel, send `\032`, `expect "Stopped"`, `exec ps -o stat= -p $pid` → `T`, send `fg\r`, expect a redraw (sentinel again) and that a following `y` reaches a pending review (raw mode restored). Measured template: `/tmp/jev-tui-bench/ctrlz-fg.exp` (§10.1). Also assert the checkpoint was *not* written by the suspend (suspend is not shutdown).

### 12.8 CI viability without a TTY
- GitHub Actions has no pty: issue "Not a tty · actions/runner #241" (`echo "$(tty)"` prints `not a tty`; workarounds tried: `docker run -t`, `python -c 'import pty; pty.spawn("/bin/sh")'`) (https://github.com/actions/runner/issues/241, 2026-09-20). Actions sets `CI` "Always set to `true`." (https://docs.github.com/en/actions/reference/workflows-and-actions/variables, 2026-09-20).
- Ink under `CI`: `const check = key => key in env && env[key] !== '0' && env[key] !== 'false'; const isInCi = check('CI') || check('CONTINUOUS_INTEGRATION');` (`node_modules/is-in-ci/index.js`) → `interactive = false` → "Only the final frame of non-static output is written at unmount", no resize listener, no sync output (readme §Continuous Integration / `interactive`). Note an **empty** `CI=` still counts as CI. Gemini patches the module to always return `false` (research 05 §1.4). For JevCode: (a) unit + ink-testing-library tests are TTY-free and unaffected (debug mode ignores `interactive`); (b) pty tests spawn with an explicit env that omits `CI` (as `render-lag.ts` already does: `env: { PATH, HOME, TERM: 'xterm-256color' }`); (c) `--plain` smoke tests run everywhere; (d) pty tests need `expect`: present at `/usr/bin/expect` and `/usr/bin/script` on macOS (measured), `apt-get install -y expect` on ubuntu runners (util-linux `script` is present); Python 3 `pty.spawn` is a fallback without extra packages but does not resize. Mark the `pty` project `skipIf(!existsSync('/usr/bin/expect'))` and run it on `macos-latest`.

### 12.9 Test hygiene specific to Ink
- Always `unmount()`/`cleanup()` (ink-testing-library exports `cleanup`) — Ink registers a `signal-exit` handler per instance.
- Timers: the spinner (`setInterval` 125 ms, `unref()`) and the 50 ms coalescer make frames time-dependent; tests assert on the last stable frame after `tick()` and never on `frames.length` exact values (only bounds, as `app.test.tsx` does: `expect(frames.length - framesBefore).toBeLessThan(10)`).
- ink-testing-library `Stdin.isTTY = true` means `useInput` is active; to test the "piped stdin" path construct a `Stdin` with `isTTY` undefined and assert `<App>` mounts without throwing (already required by DESIGN §14).

## OPEN QUESTIONS

1. Claude Code's 50 ms "pre-park" (cursor to column 0, wait, then write) before each changed line: Ink writes erase+text in one chunk; is a custom `stdout` wrapper that splits the write worth it, and does VoiceOver on macOS Terminal actually need it? Needs a real screen-reader session to answer.
2. Apple Terminal: does it answer `OSC 11 ; ?` and does it set `COLORFGBG`? Not testable from this non-TTY session; vtdn does not list it. Decide after a manual check before any `/theme detect` work.
3. `fullStaticOutput` growth: track Ink PR #1005; if it lands in a 7.1.x release, the item cap can rise and the remount can go.
4. Should `--screen-reader` on a TTY use the Ink SR path (still an in-place status line) or fall back to the readline `--plain` composer entirely (pure append-only)? Codex #11823 users asked for "append-oriented updates"; a user test with NVDA/VoiceOver should decide.
5. Grapheme vs code-point cursor semantics for `Ctrl-W`/word motion in CJK text (no spaces): adopt `Intl.Segmenter({granularity:'word'})`? Cost and correctness untested.
6. `SSH_CONNECTION`-based fps heuristic: is 10 fps right, and should it also lower the 50 ms coalescer? Measure over a throttled pty (e.g. `pv -L`) before shipping.
7. Exact POSIX wording for stop signals in orphaned process groups (explains the `expect` Ctrl-Z result) — cite `kill()`/XSH signal-generation text once located.
8. Does `--plain` need a bell option too (`preferredNotifChannel`-style) for long runs without a screen reader?

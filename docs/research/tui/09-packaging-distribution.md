# 09 — Packaging, installation and startup for the JevCode CLI/TUI

Research date: **2026-09-20**. Every claim carries its source URL and the fetch date in parentheses. Primary sources are raw files from the four repositories (`raw.githubusercontent.com`), npm registry JSON, the Claude Code npm tarball itself, the Node 22 API docs, and files installed under `node_modules/`. Measurements were made in `/tmp` on the machine described in §10.0; the repository was not modified (the only new file is this one).

Scope: how opencode, Claude Code, Gemini CLI and Codex CLI *ship* (npm layout, native binaries, installers, Homebrew, releases, upgrade, completions, telemetry, config dirs, Windows, signing), then Node-native startup options for JevCode with local numbers, then a concrete packaging plan.

Hard constraints respected throughout (from the task): Node 22 (pinned 22.23.2), TS strict/no `any`, ESM, **one** npm package, runtime deps only `ink@7.1.1` + `react@19.3.0`, esbuild single-file bundle, first frame < 300 ms with zero network at launch, no terminal clears after the first frame, keys never in logs.

## 1. How each tool ships (primary sources)

### 1.1 opencode (anomalyco/opencode, branch `dev`)

- **Monorepo, private package**: `packages/opencode/package.json` has `"name": "opencode"`, `"type": "module"`, `"private": true`, `"bin": { "opencode": "./bin/opencode" }`, `"exports": { "./*": "./src/*.ts" }`, scripts `"build": "bun run script/build.ts"`, `"typecheck": "tsgo --noEmit"`; no `engines`, no `files` (https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/opencode/package.json, 2026-09-20).
- **Build = Bun compile per target**: `script/build.ts` enumerates 12 targets (`linux/darwin/win32` × `arm64/x64`, plus `avx2: false` "baseline" x64 variants and `abi: "musl"`), then `Bun.build({ … compile: { target: name.replace(pkg.name, "bun"), outfile: \`dist/${name}/bin/opencode\`, execArgv: [\`--user-agent=opencode/${Script.version}\`, "--use-system-ca", "--"] }, minify: true, splitting: true })`. Each `dist/<name>/package.json` is written as `{ name, version, preferUnplugged: true, os: [item.os], cpu: [item.arch], libc?: [item.abi] }`. A smoke test runs `<binary> --version` for the host target. On release: `tar -czf` for linux, `zip -r` otherwise, then `gh release upload v${Script.version} ./dist/*.zip ./dist/*.tar.gz --clobber` (https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/opencode/script/build.ts, 2026-09-20). Note the comment `// changing to win32 flags npm for some reason` → packages are named `opencode-windows-x64`, not `win32`.
- **npm wrapper `opencode-ai`**: registry shows `"bin": { "opencode": "bin/opencode.exe" }`, `"scripts": { "postinstall": "node ./postinstall.mjs" }`, 12 `optionalDependencies` (`opencode-linux-x64`, `…-baseline`, `…-musl`, `…-baseline-musl`, darwin x64/arm64 (+baseline), windows x64/arm64 (+baseline)), `unpackedSize` 7,865, `fileCount` 4, attestations present; the arm64 mac binary package is 144,470,642 B unpacked, 2 files (https://registry.npmjs.org/opencode-ai/latest and https://registry.npmjs.org/opencode-darwin-arm64/latest, 2026-09-20).
- **postinstall** (`script/postinstall.mjs`) computes candidate package names (AVX2 probe: `/proc/cpuinfo` on Linux, `sysctl -n hw.optional.avx2_0` on macOS, PowerShell `IsProcessorFeaturePresent(40)` on Windows; musl: `/etc/alpine-release` or `ldd --version`), then `require.resolve(\`${name}/package.json\`)`, `fs.linkSync(source, target)` falling back to `copyFileSync`, `chmodSync(target, 0o755)`, verifies with `spawnSync(targetBinary, ["--version"])`; if the optional dep is missing it runs `npm install --ignore-scripts --no-save --loglevel=error --prefix <tmp> <name>@<version>` itself (https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/opencode/script/postinstall.mjs, 2026-09-20). `publish.ts` writes a `bin/opencode.exe` *stub* that prints `"Error: <pkg>-ai's postinstall script was not run."` … `"package manager like pnpm that does not run postinstall scripts by default."` (https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/opencode/script/publish.ts, 2026-09-20).
- **Older Node launcher** (`bin/opencode`, still in repo): `#!/usr/bin/env node`, resolves `OPENCODE_BIN_PATH` or walks up `node_modules` for the platform package, `spawn(target, process.argv.slice(2), { stdio: "inherit" })`, forwards `SIGINT`,`SIGTERM`,`SIGHUP`, and on child signal death does `process.kill(process.pid, signal)` (https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/opencode/bin/opencode, 2026-09-20).
- **Publish**: `npm publish *.tgz --access public --tag ${Script.channel}`; channel is `"latest"` for bumps and the git branch name otherwise, with preview versions `0.0.0-${CHANNEL}-${timestamp}`; the next version is computed from `https://registry.npmjs.org/opencode-ai/latest` (https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/script/src/index.ts, 2026-09-20). Non-preview releases also push an AUR `PKGBUILD` and regenerate the Homebrew tap formula (`class Opencode < Formula … on_macos … url "https://github.com/anomalyco/opencode/releases/download/v${Script.version}/opencode-darwin-arm64.zip" … bin.install "opencode"`), committed to `anomalyco/homebrew-tap` (publish.ts, same fetch). The tap file itself says `# This file was generated by GoReleaser. DO NOT EDIT.` and `depends_on "ripgrep"` (https://raw.githubusercontent.com/anomalyco/homebrew-tap/master/opencode.rb, 2026-09-20).
- **CI**: `.github/workflows/publish.yml` builds the CLI on `blacksmith-4vcpu-ubuntu-2404` with Bun, uploads `opencode-darwin*`/`opencode-linux*` artifacts, has a `sign-cli-windows` job on `blacksmith-4vcpu-windows-2025` using `azure/artifact-signing-action` and `Get-AuthenticodeSignature` verification, then `gh release upload … --clobber`; macOS signing/notarization (`apple-actions/import-codesign-certs`, `APPLE_API_KEY`) appears in the desktop (electron-builder) job, not the CLI job (https://raw.githubusercontent.com/anomalyco/opencode/dev/.github/workflows/publish.yml, 2026-09-20).
- **Install script** (`install`, served identically at https://opencode.ai/install): `INSTALL_DIR=$HOME/.opencode/bin`; detects os/arch, Rosetta (`sysctl -n sysctl.proc_translated`), musl and AVX2 the same way as postinstall; downloads `https://github.com/anomalyco/opencode/releases/latest/download/$filename` (or a `--version`), verifies the tag exists with a HEAD request, unzips/untars, `chmod 755`; then appends `export PATH=$INSTALL_DIR:\$PATH` (or `fish_add_path`) to the first existing shell rc among `${ZDOTDIR:-$HOME}/.zshrc … $XDG_CONFIG_HOME/zsh/.zshrc`, `~/.bashrc …`, `~/.config/fish/config.fish`, unless `--no-modify-path`; in GitHub Actions it appends to `$GITHUB_PATH` (https://raw.githubusercontent.com/anomalyco/opencode/dev/install, 2026-09-20). No checksum verification is performed.
- **Upgrade command**: `command: "upgrade [target]"`, `describe: "upgrade opencode to the latest or a specific version"`, `--method`/`-m` with `choices: ["curl", "npm", "pnpm", "bun", "brew", "choco", "scoop"]`; if the detected method is `"unknown"` it warns `opencode is installed to ${process.execPath} and may be managed by a package manager` and asks "Install anyways?" (https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/opencode/src/cli/cmd/upgrade.ts, 2026-09-20). Detection (`installation/index.ts`): `process.execPath.includes(path.join(".opencode","bin"))` or `(".local","bin")` → `curl`; otherwise it shells out to `npm list -g --depth=0`, `yarn global list`, `pnpm list -g --depth=0`, `bun pm ls -g`, `brew list --formula opencode`, `scoop list opencode`, `choco list --limit-output opencode`. Latest version per method: `brew info --json=v2` / `https://formulae.brew.sh/api/formula/opencode.json`, npm registry, Chocolatey OData, Scoop, else `https://api.github.com/repos/anomalyco/opencode/releases/latest`. Upgrade runs e.g. `npm install -g opencode-ai@${target}`, `brew tap anomalyco/tap` + `brew upgrade <formula>`, `choco upgrade opencode --version=${target} -y`, `scoop install opencode@${target}` (https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/opencode/src/installation/index.ts, 2026-09-20).
- **XDG**: `packages/core/src/global.ts` imports `{ xdgData, xdgCache, xdgConfig, xdgState } from "xdg-basedir"` and defines `data = xdgData/opencode`, `cache`, `config`, `state`, `bin: path.join(cache, "bin")`, `log: path.join(data, "log")`, `tmp: os.tmpdir()/opencode`; `config` can be overridden by `Flag.OPENCODE_CONFIG_DIR`; all dirs are `mkdir`'d at module load (https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/core/src/global.ts, 2026-09-20; dependency `xdg-basedir 5.1.0` in https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/core/package.json, 2026-09-20). `xdg-basedir` defaults: `XDG_DATA_HOME || ~/.local/share`, `XDG_CONFIG_HOME || ~/.config`, `XDG_STATE_HOME || ~/.local/state`, `XDG_CACHE_HOME || ~/.cache` on every OS including macOS (https://raw.githubusercontent.com/sindresorhus/xdg-basedir/main/index.js, 2026-09-20).
- **CLI shell**: yargs with `.scriptName("opencode")`, `.completion("completion", "generate shell completion script")`, `.strict()`, global `--print-logs`, `--log-level`, `--pure`; the TUI command calls `client.call("checkUpgrade", …)` after start (https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/opencode/src/index.ts and …/src/cli/cmd/tui.ts, 2026-09-20). Docs: `autoupdate` accepts `true`, `false` or `"notify"`; config precedence lists `~/.config/opencode/opencode.json`, `OPENCODE_CONFIG`, project `opencode.json`, `OPENCODE_CONFIG_CONTENT`, managed dirs `/Library/Application Support/opencode/`, `/etc/opencode/`, `%ProgramData%\opencode` (https://opencode.ai/docs/config/, 2026-09-20). Install docs: `brew install anomalyco/tap/opencode`, `npm install -g opencode-ai`, `choco install opencode`, `scoop install opencode`, `paru -S opencode-bin`; Windows: "For the best experience on Windows, we recommend using Windows Subsystem for Linux (WSL)." and "Support for installing OpenCode on Windows using Bun is currently in progress." (https://opencode.ai/docs/, 2026-09-20).
- **homebrew-core formula** builds from source with Bun: `depends_on "bun" => :build`, `depends_on "ripgrep"`, `inreplace "packages/opencode/script/build.ts", "splitting: true,", "splitting: false,"`, `system "bun", "--bun", "./script/build.ts", "--single", "--skip-install"`, `generate_completions_from_executable(bin/"opencode", "completion", shell_parameter_format: :none, shells: [:zsh])`, `deny_network_access! :test`, test sets `OPENCODE_DISABLE_MODELS_FETCH=1` (https://raw.githubusercontent.com/Homebrew/homebrew-core/HEAD/Formula/o/opencode.rb, 2026-09-20).

### 1.2 Claude Code (npm `@anthropic-ai/claude-code`, tarball inspected)

- **Registry**: `"bin": {"claude":"bin/claude.exe"}`, `"engines": {"node":">=22.0.0"}`, `"type":"module"`, `"scripts": { "prepare": "node -e \"if (!process.env.AUTHORIZED) { console.error('ERROR: Direct publishing is not allowed.…') }\"", "postinstall": "node install.cjs" }`, `dependencies: {}`, 8 `optionalDependencies` (`…-darwin-arm64`, `-darwin-x64`, `-linux-x64`, `-linux-arm64`, `-linux-x64-musl`, `-linux-arm64-musl`, `-win32-x64`, `-win32-arm64`, all `2.1.278`), `unpackedSize` 184,119, 7 files (https://registry.npmjs.org/@anthropic-ai/claude-code/latest, 2026-09-20). The arm64 mac binary package: `"os":["darwin"],"cpu":["arm64"]`, 217,695,985 B unpacked, 4 files (https://registry.npmjs.org/@anthropic-ai/claude-code-darwin-arm64/latest, 2026-09-20).
- **Tarball contents** (`claude-code-2.1.278.tgz`, 27,538 B): `package.json`, `install.cjs`, `cli-wrapper.cjs`, `bin/claude.exe` (500 B ASCII shell stub: `echo "Error: claude native binary not installed." >&2 … exit 1`), `sdk-tools.d.ts`, `README.md`, `LICENSE.md`; `"files": ["bin/claude.exe","install.cjs","cli-wrapper.cjs","sdk-tools.d.ts"]` (https://registry.npmjs.org/@anthropic-ai/claude-code/-/claude-code-2.1.278.tgz, 2026-09-20).
- **install.cjs (postinstall)**: header comment: "Detects the platform, finds the matching native binary from optionalDependencies, and copies it over the bin/claude.exe placeholder. After this runs, `claude` execs the native binary directly — no Node.js process stays resident." musl detection: `process.report.getReport().header.glibcVersionRuntime === undefined` ("Faster than spawning `ldd` and avoids the ENOENT→musl false positive"). Rosetta: `sysctl -n sysctl.proc_translated` → prefer arm64 ("the x64 build needs AVX, which Rosetta doesn't emulate"). Placement: `linkSync(src, dest)` first ("instant, zero extra disk for a ~500MB binary"), `EEXIST` → read stub (`statSync(dest).size < 4096`) → unlink → link → `copyFileSync`, restoring the stub on failure; `EXDEV`/`EPERM` → copy. Why `.exe`: "The .exe extension + no-shebang stub makes npm's cmd-shim (generated at install time, before postinstall) emit a direct exec on Windows; Unix ignores the extension. Same pattern as Bun's npm package." (tarball `install.cjs`, 2026-09-20).
- **cli-wrapper.cjs (fallback)**: "exists for environments where postinstall doesn't run (--ignore-scripts)"; `spawnSync(binaryPath, process.argv.slice(2), { stdio: 'inherit', env: { …, CLAUDE_CODE_INSTALLED_VIA_NPM_WRAPPER: '1' } })`; on signal: "Node.js ignores some signals (e.g. SIGPIPE → SIG_IGN), so re-raising is unreliable. Exit with the POSIX convention 128+signum instead." (tarball `cli-wrapper.cjs`, 2026-09-20).
- **install.sh** (https://claude.ai/install.sh, 2026-09-20): refuses `sudo` from a user shell unless `CLAUDE_INSTALL_ALLOW_SUDO=1`; `DOWNLOAD_BASE_URL="https://downloads.claude.ai/claude-code-releases"`, `DOWNLOAD_DIR="$HOME/.claude/downloads"`; supports `curl` or `wget`, optional `jq` and `zstd`; `version=$(download_file "$DOWNLOAD_BASE_URL/latest")` then `manifest.json` → `platforms[$platform].checksum` (64-hex, validated) and `size`; downloads `claude.zst` when zstd is present, else `claude`, verifies `sha256sum`/`shasum -a 256`, then runs `"$binary_path" install ${TARGET:+"$TARGET"}` (the binary installs its own launcher) and deletes the download; Windows shells are rejected ("Windows is not supported by this script."); exit 137 on Linux is explained as OOM ("Claude Code needs roughly 512MB of free memory to install").
- **Docs (setup)**: recommended `curl -fsSL https://claude.ai/install.sh | bash`, `irm https://claude.ai/install.ps1 | iex`, `brew install --cask claude-code` ("`claude-code` tracks the stable release channel … `claude-code@latest` tracks the latest channel"), `winget install Anthropic.ClaudeCode`, signed apt/dnf/apk repos; "Native installations automatically update in the background"; launcher "at `~/.local/bin/claude` as a symlink into `~/.local/share/claude/versions/`"; `autoUpdatesChannel: "latest"|"stable"`, `minimumVersion`; `DISABLE_AUTOUPDATER` "only stops the background check; `claude update` and `claude install` still work. To block all update paths … set `DISABLE_UPDATES`"; `claude update` reports `Successfully updated from <old version> to version <new version>`; npm: "As of v2.1.198, the npm package requires Node.js 22 or later. On an older Node.js version, npm prints an `EBADENGINE` warning during install rather than failing"; "To upgrade an npm installation, run `npm install -g @anthropic-ai/claude-code@latest`. Avoid `npm update -g`"; `CLAUDE_CODE_PACKAGE_MANAGER_AUTO_UPDATE=1` lets it run `brew`/`winget` upgrades itself; binaries: "macOS: signed by 'Anthropic PBC' and notarized by Apple. Verify with `codesign --verify --verbose ./claude`", "Windows: signed by 'Anthropic, PBC'", Linux: not code-signed, verify the GPG-signed `manifest.json` (fingerprint `31DD DE24 DDFA B679 F42D 7BD2 BAA9 29FF 1A7E CACE`); `claude doctor` "prints read-only installation and settings diagnostics" (https://code.claude.com/docs/en/setup, 2026-09-20).
- **Windows**: native (PowerShell/CMD installers, `Git for Windows` optional for the Bash tool, sandboxing "Not supported") or WSL 2 (sandboxing "Supported") (same page).
- **Telemetry**: "Metrics … Set `DISABLE_TELEMETRY=1` to opt out"; "Error reports … Set `DISABLE_ERROR_REPORTING=1`"; "disable all non-essential traffic at once by setting `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`"; surveys disabled when "`DISABLE_TELEMETRY`, `DO_NOT_TRACK`, or `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` is set"; "By default, error reporting, telemetry, and bug reporting are disabled when using Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry" (https://code.claude.com/docs/en/data-usage, 2026-09-20).
- **Dirs**: `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json`, `~/.claude.json`; "On Windows, `~/.claude` means `%USERPROFILE%\.claude`. To keep the home-directory files somewhere else, set `CLAUDE_CONFIG_DIR`" (https://code.claude.com/docs/en/settings, 2026-09-20). The cask's `zap` lists `~/.cache/claude`, `~/.config/claude`, `~/.local/bin/claude`, `~/.local/share/claude`, `~/.local/state/claude`, `~/Library/Caches/claude-cli-nodejs`, `rmdir: "~/.claude"`; cask uses `binary "claude"`, `url "https://downloads.claude.ai/claude-code-releases/#{version}/#{os}-#{arch}/claude"`, `livecheck url ".../stable"`, `conflicts_with cask: "claude-code@latest"` (https://raw.githubusercontent.com/Homebrew/homebrew-cask/HEAD/Casks/c/claude-code.rb, 2026-09-20).

### 1.3 Codex CLI (openai/codex)

- **npm wrapper**: `codex-cli/package.json`: `"name": "@openai/codex"`, `"version": "0.0.0-dev"`, `"bin": { "codex": "bin/codex.js" }`, `"type": "module"`, `"engines": { "node": ">=16" }`, `"files": ["bin/codex.js"]`, `"packageManager": "pnpm@10.34.5+sha512…"` (https://raw.githubusercontent.com/openai/codex/main/codex-cli/package.json, 2026-09-20). Registry 0.155.1: `optionalDependencies` are **aliases** — `"@openai/codex-darwin-arm64": "npm:@openai/codex@0.155.1-darwin-arm64"` etc. (the platform builds are published as pre-release versions of the *same* package; `https://registry.npmjs.org/@openai%2fcodex-darwin-arm64` returns `{"error":"Not found"}`), `unpackedSize` 13,206, 3 files, `attestations.provenance.predicateType: "https://slsa.dev/provenance/v1"` (https://registry.npmjs.org/@openai/codex/latest, 2026-09-20). `build_npm_package.py` documents it: "`npm_name` is the local optional-dependency alias consumed by `bin/codex.js`. The underlying package published to npm is always `@openai/codex`." and writes `optionalDependencies = { npm_name: f"npm:{CODEX_NPM_NAME}@{compute_platform_package_version(version, npm_tag)}" }` (https://raw.githubusercontent.com/openai/codex/main/codex-cli/scripts/build_npm_package.py, 2026-09-20).
- **bin/codex.js**: maps `process.platform/arch` to a target triple (linux → `*-unknown-linux-musl`, i.e. static musl builds serve glibc hosts too), `require.resolve(\`${platformPackage}/package.json\`)` → `vendor/<triple>/bin/codex[.exe]`; error text `Missing optional dependency ${platformPackage}. ## 2. npm package layout lessons

- `bin`: "Please make sure that your file(s) referenced in bin starts with #!/usr/bin/env node, otherwise the scripts are started without the node executable!"; on install "in case of unix-like OS it'll create a symlink from the cli.js script to /usr/local/bin/myapp and in case of windows it will create a cmd file usually at C:\Users\{Username}\AppData\Roaming\npm\myapp.cmd" (https://docs.npmjs.com/cli/v10/configuring-npm/package-json, 2026-09-20). cmd-shim: "The cmd-shim used in npm to create executable scripts on Windows, since symlinks are not suitable for this purpose there." (https://raw.githubusercontent.com/npm/cmd-shim/main/README.md, 2026-09-20).
- `files`: "Certain files are always included, regardless of settings: package.json README LICENSE / LICENCE The file in the "main" field The file(s) in the "bin" field"; `.npmrc` is always ignored (same npm page). JevCode's current `"files": ["bin", "dist", "README.md", "docs"]` would ship `dist/jevcode.mjs.map` (2,551,697 B) and `dist/meta.json` (312,553 B) and 3,800-line design docs (local `ls -la dist`, 2026-09-20).
- `engines`: "Unless the user has set the engine-strict config flag, this field is advisory only and will only produce warnings when your package is installed as a dependency." (same page); `engine-strict`: "If set to true, then npm will stubbornly refuse to install (or even consider installing) any package that claims to not be compatible with the current Node.js version." (https://docs.npmjs.com/cli/v10/using-npm/config, 2026-09-20). The repo's `.npmrc` (`engine-strict=true`, `save-exact=true`) is a *consumer-side* setting: it protects contributors, not end users. Claude Code's docs confirm the end-user effect: EBADENGINE is a warning.
- `optionalDependencies`: "build failures do not cause installation to fail. Running npm install --omit=optional will prevent these dependencies from being installed. It is still your program's responsibility to handle the lack of the dependency." (package.json page). `os`/`cpu` fields restrict per-platform packages (`"os": ["darwin"], "cpu": ["arm64"]` as used by all three binary shippers); `libc` exists only in `devEngines` per the fetched page — the shippers encode musl in the *package name* instead.
- `man`: "Specify either a single file or an array of filenames to put in place for the man program to find." (package.json page) — none of the four ships a man page via npm.
- `npx`: "If any requested packages are not present in the local project dependencies, then they are installed to a folder in the npm cache, which is added to the PATH environment variable in the executed process. A prompt is printed (which can be suppressed by providing either --yes or --no)." (https://docs.npmjs.com/cli/v10/commands/npx, 2026-09-20). Gemini detects npx runs by `/.npm/_npx` in the realpath and disables self-update.
- Pattern shared by opencode and Claude Code: **placeholder `bin/<name>.exe` + postinstall hard-link** so Windows gets a direct exec shim and `--ignore-scripts` installs still print a helpful error. Codex instead keeps a Node launcher and pays a Node process per invocation.

## 3. Native installers, GitHub Releases, Homebrew

## 9. Provenance and signing

- npm provenance: "When an npm package is published with provenance, it is signed by Sigstore public good servers and logged in a public transparency ledger"; requires a "supported cloud CI/CD provider using a cloud-hosted runner. Today this includes GitHub Actions and GitLab CI/CD"; `npm publish --provenance --access public` with workflow `permissions: contents: read, id-token: write` (https://docs.npmjs.com/generating-provenance-statements, 2026-09-20).
- Trusted publishing: "publish npm packages directly from your CI/CD workflows using OpenID Connect (OIDC) authentication, eliminating the need for long-lived npm tokens"; "requires npm CLI version 11.5.1 or later and Node version 22.14.0 or higher"; "When you publish using trusted publishing from GitHub Actions or GitLab CI/CD, npm automatically generates and publishes provenance attestations … you don't need to add the --provenance flag" (https://docs.npmjs.com/trusted-publishers, 2026-09-20). Codex's registry entry shows the result (`slsa.dev/provenance/v1`); opencode's shows `attestations` too; Claude and Gemini show only registry signatures (§1).
- Binary signing: Claude — Apple notarization + Authenticode + GPG-signed manifest + signed apt/dnf/apk (§1.2); Codex — `rcodesign` via Azure Key Vault, notarize, cosign for Linux (§1.3); opencode — Azure Trusted Signing for Windows CLI (§1.1); Gemini SEA — `codesign --options runtime --timestamp` with entitlements (§1.4). Node's own SEA docs require `codesign --remove-signature` before injection and `codesign --sign - hello` after (https://nodejs.org/docs/latest-v22.x/api/single-executable-applications.html, 2026-09-20).

Apple M5 Pro (15 cores, 24 GiB), macOS 26.6.2 (`sw_vers`), `node v22.23.2` arm64, V8 `12.4.254.21-node.56`, node binary 112,937,728 B at `~/.local/node/node-v22.23.2-darwin-arm64/bin/node` (all from local commands, 2026-09-20). Two harnesses, both spawn a fresh process per run and report the parent's `performance.now()` delta (spawn → exit, or spawn → first pty byte containing the sentinel `step 0/`), plus the child's own `FIRST_FRAME_MS` (child clock, excludes ~9 ms of Node boot: `node -e 'console.log(performance.now())'` prints 8.2–9.8 ms):

- `/tmp/jevbench/time-first-frame.mjs <launcher> <n> <label>`: `node <launcher> run x --workspace <tmp> --plain --perf-exit-after-first-frame` with `JEVCODE_HOME=<tmp>/no-runs`, `JEVCODE_ASSERT_NO_NETWORK=1`, `NODE_COMPILE_CACHE=<fresh tmp dir>` (first run cold, rest warm). This is the task's command; note `--plain` never imports Ink (`main.tsx` picks `tui/plain.js`), so it measures Node + bundle load + plain renderer only.
- `/tmp/jevbench/pty-first-frame.mjs <launcher> <n> <label>` (mirrors `src/perf/first-frame.ts`): `/usr/bin/script -q /dev/null sh -c 'stty rows 40 cols 120; exec node <launcher> run "perf probe" --workspace <tmp> --config <tmp>/no-such-config.json --perf-exit-after-first-frame'`, env `TERM=xterm-256color`, same JEVCODE vars; `COLD=1` uses a fresh `NODE_COMPILE_CACHE` per run. Also counts `\x1b[2J` (always 0 below).
- Build variants were produced with the repo's esbuild 0.28.2 from `src/cli/main.tsx` into `/tmp/jevbuild` (same options as `scripts/build.mjs`, `sourcemap: false`). The repo's own `dist/jevcode.mjs` (1,576,081 B, built 08:04) predates today's uncommitted `src/synth/*` additions; a fresh unminified build is 2,171,500 B (the `synth` chunk alone is 516,092 B in the split build), so variant comparisons use freshly built files only.

### 10.2 `module.enableCompileCache()` (already in `bin/jevcode.js`)

Docs: "Enable module compile cache in the current Node.js instance"; `NODE_COMPILE_CACHE=dir` (v22.1.0) and `NODE_DISABLE_COMPILE_CACHE=1` (v22.8.0), Stability 1.1 (https://nodejs.org/docs/latest-v22.x/api/module.html and …/cli.html, 2026-09-20). `NODE_DEBUG_NATIVE=COMPILE_CACHE` confirmed hits: `reading cache … for ESM file:///private/tmp/jevbuild/esm.mjs...[… 2171500 374480 …]... success, size=374480` (cache entry 374 KB for the 2.17 MB bundle; cache dir 388 KB, 6 files).

| Path | cache ON | cache OFF (`NODE_DISABLE_COMPILE_CACHE=1`) | cold (fresh dir) |
|---|---|---|---|
| `--version` (whole bundle compiled eagerly), n=20 | **26.7 ms** (repeat 27.2) | **38.5 ms** | 38.3 (first run above) |
| TUI pty first frame, n=15 | 82.4 ms (repeat 81.4) | 82.4 ms | 95.5 (n=10) |

Reading: the cache saves ~12 ms (30%) on paths that only parse/compile the bundle, but **nothing measurable on the TUI first frame**, whose cost is module *evaluation* (Ink/React/yoga init + first render), not compilation; a cold run pays ~13 ms extra to *write* the cache. Keep it (it helps `--help`, `--version`, `config`, `completion`), do not expect it to move the TUI number.

### 10.3 Minification

`minify: true` → 2,171,500 → **1,079,297 B** (gzip 500,542 → 369,768). Timings (same harnesses): `--version` 26.9 → 25.2 ms; `--plain` first frame 28.4 → 26.8 ms; TUI warm 82.6 → 81.6 ms; TUI cold 95.5 → 92.7 ms; TUI with cache off 82.5 → 82.5. Effect: −1…−3 ms, i.e. tarball size is the real win. Cost: mangled identifiers in stack traces unless `keepNames: true` or a sourcemap is shipped (not measured separately).

### 10.4 Code splitting (lazy dynamic imports as real chunks)

Today every `await import('../x.js')` in `main.tsx` is folded into the single file (esbuild turns them into lazily *evaluated* but eagerly *parsed* wrappers). With `splitting: true, outdir` esbuild emits 47 files: `main.js` 26,424 B, `chunks/App-*.js` 873,625 B (Ink+React+yoga+TUI), `chunks/synth-*.js` 516,092 B, `chunks/runner-*.js` 149,246 B (bench), `chunks/devtools-*.js` 128,723 B, providers ~10 KB each, `plain-*.js` 1,291 B. Timings: `--version` **21.6 ms** (vs 26.9 single); TUI warm **78.4** (vs 82.6), cold **84.5** (vs 95.5). So splitting saves 4–11 ms on the TUI and 5 ms on every non-TUI command, at the price of the "single file" property (`files` must ship `dist/chunks/`). Recorded for the decision table; not adopted below because of the stated constraint.

### 10.5 Where the TUI's ~80 ms goes

A bare bundle `import { render, Text } from 'ink'; import React from 'react'` (972,878 B) reaches the statement after the imports at **41.6–46.5 ms** on the child clock (n=5; 50.9 ms wall n=15), and a one-`<Text>` `render()` + `waitUntilRenderFlush()` finishes at 49.4–52.4 ms under a pty. JevCode's App reaches its first frame at 77.9–79.7 ms child clock. Decomposition: Node boot ≈ 9 ms → Ink+React+yoga module evaluation ≈ 33 ms (includes yoga's WASM instantiation via `await loadYoga()` top-level await in `yoga-layout/dist/src/index.js:13`) → first render ≈ 6 ms → JevCode's own modules, reducer, `<Static>`, panes ≈ 28 ms. The dominant fixed cost is Ink/React/yoga evaluation, which no cache can remove (§10.6).

### 10.6 `node --build-snapshot` / `--snapshot-blob`

Docs: "--build-snapshot Added in: v18.8.0 Stability: 1 - Experimental"; "User-land modules are not yet supported in the snapshot, so only one single file can be snapshotted. Users can bundle their applications into a single script with their bundler of choice before building a snapshot, however."; "Only a subset of the built-in modules work in the snapshot" (https://nodejs.org/docs/latest-v22.x/api/cli.html, 2026-09-20); `v8.startupSnapshot` API "v22.17.0 Marking the API stable" but "Currently the application deserialized from a user-land snapshot cannot be snapshotted again" (https://nodejs.org/docs/latest-v22.x/api/v8.html, 2026-09-20). Attempts:

1. `node --snapshot-blob /tmp/jevsnap/esm.blob --build-snapshot /tmp/jevbuild/esm.mjs` → `SyntaxError: Cannot use import statement outside a module at minimalRunCjs (node:internal/main/mksnapshot:207:16)` — the snapshot entry is run as CommonJS.
2. CJS wrapper `import("/tmp/jevbuild/esm.mjs")` under `--build-snapshot` → `Error: Not supported at minimalRunCjs (node:internal/main/mksnapshot:208:12)` — dynamic `import()` is disabled in the snapshot builder.
3. Emitting a CJS bundle with esbuild (`format: 'cjs'`) fails: `Top-level await is currently not supported with the "cjs" output format` at `node_modules/yoga-layout/dist/src/index.js:13` (`const Yoga = wrapAssembly(await loadYoga());`), `node_modules/ink/build/reconciler.js:23` and `:73`, `node_modules/ink/build/devtools.js:27` — Ink 7.1.1 and yoga-layout 3.2.1 are TLA-ESM only.
4. `new WebAssembly.Module(bytes)` inside a snapshot builder script → `ReferenceError: WebAssembly is not defined` — yoga's engine could not be captured even if the module graph could.
5. Reference: a builtins-only CJS script snapshot (blob 5,934,643 B, warning "It's not yet fully verified whether built-in module "node:child_process" works in user snapshot builder scripts") starts in 19.1 ms vs 18.4 ms for the plain script (n=15) — no gain at JevCode's size class.

Verdict: **not usable** with the Ink bundle on Node 22.

### 10.7 Node SEA (single executable application)

Docs: "The single executable application feature currently only supports running a single embedded script using the CommonJS module system."; config fields `main`, `output`, `disableExperimentalSEAWarning`, `useSnapshot`, `useCodeCache`, `execArgv`, `assets`; "The version of the Node.js binary used to produce the blob must be the same as the one to which the blob will be injected."; "Note: import() does not work when useCodeCache is true."; injected-script `require()` "can only be used to load built-in modules"; cross-platform builds must set `useCodeCache`/`useSnapshot` false; macOS steps `codesign --remove-signature` → `npx postject hello NODE_SEA_BLOB sea-prep.blob --sentinel-fuse NODE_SEA_FUSE_fce680ab2cc467b6e072b8b5df1996b2 --macho-segment-name NODE_SEA` → `codesign --sign - hello` (https://nodejs.org/docs/latest-v22.x/api/single-executable-applications.html, 2026-09-20; postject 1.0.0-alpha.6, https://registry.npmjs.org/postject/latest, 2026-09-20). `data:` imports are supported for `text/javascript` (https://nodejs.org/docs/latest-v22.x/api/esm.html, 2026-09-20).

Feasibility build in `/tmp/jevsea` (postject installed there, not in the repo): a minified ESM bundle with `define: { 'import.meta.url': '"file:///tmp/jevsea/bundle.mjs"' }` and banner `const require = createRequire('/tmp/jevsea/bundle.mjs')` embedded as asset `bundle.mjs`; CJS `main`:

- **Variant A** (`sea-main.cjs`): `import('data:text/javascript;base64,' + Buffer.from(getAsset('bundle.mjs','utf8')).toString('base64'))`. `sea-config.json`: `{ "main": "/tmp/jevsea/sea-main.cjs", "output": "/tmp/jevsea/sea-prep.blob", "disableExperimentalSEAWarning": true, "useCodeCache": true, "useSnapshot": false, "assets": { "bundle.mjs": "/tmp/jevsea/bundle.mjs" } }`; `node --experimental-sea-config sea-config.json`; `cp $(realpath $(command -v node)) ./jevcode-sea; codesign --remove-signature ./jevcode-sea; npx --no-install postject ./jevcode-sea NODE_SEA_BLOB sea-prep.blob --sentinel-fuse NODE_SEA_FUSE_fce680ab2cc467b6e072b8b5df1996b2 --macho-segment-name NODE_SEA; codesign --sign - ./jevcode-sea`. Result: **113,113,984 B** (36,592,677 B gzip -9), `./jevcode-sea --version` → `jevcode 0.1.0`, `--plain --perf-exit-after-first-frame` prints `FIRST_FRAME_MS=46.9` and exits 0. Timings: `--version` **54.4 ms** (n=15), `--plain` first frame **55.1 ms** (n=12), TUI pty **107.5 ms** (n=10) — slower than `node bin/jevcode.js` (26/27/82) because a `data:` module gets no compile cache and the 1.4 MB base64 string is built per start.
- **Variant B** (`sea-main-b.cjs`): on first run write the asset to `${XDG_CACHE_HOME:-~/.cache}/jevcode/bundle-<ver>/bundle.mjs` (tmp + `renameSync`), then `import(pathToFileURL(file).href)` with `enableCompileCache()`. Timings: first run `--version` **94.4 ms** (extract + cold compile), then **24.0 ms** (n=15); `--plain` first frame **24.6 ms**; TUI pty **80.4 ms** warm (n=10), first ever run 114.3 ms. Binary 113,130,400 B. No experimental warning printed.

Verdict: SEA **works** for this bundle (via `import()` of an asset; `useSnapshot` is impossible for the reasons in §10.6, `useCodeCache` cannot be combined with `import()`), but it gives **parity, not a speedup** (variant B ≈ node+bundle), costs 113 MB per platform (Gemini's experiment is the same shape), must be built per platform on the exact Node version, and needs codesign/notarization handling. Its only benefit is "no Node required", which none of JevCode's target users (developers with Node 22) need today.

## 11. Recommended packaging plan for JevCode

### 11.1 package.json (publishable, still one package, zero install-time dependencies)

```jsonc
{
  "name": "jevcode",
  "version": "0.1.0",                       // single source of truth: inject into the bundle via esbuild define (main.tsx hard-codes VERSION today)
  "description": "…",
  "license": "MIT",                          // add a LICENSE file: the repo has none (ls LICENSE* → no match, 2026-09-20); npm always includes it
  "type": "module",
  "bin": { "jevcode": "bin/jevcode.js" },    // keep the Node launcher (shebang #!/usr/bin/env node; npm makes a .cmd shim on Windows)
  "files": ["bin/jevcode.js", "dist/jevcode.mjs", "dist/THIRD_PARTY_LICENSES.txt", "man/jevcode.1", "README.md"],  // no .map, no meta.json, no docs/
  "man": ["./man/jevcode.1"],
  "engines": { "node": ">=22.12.0 <27" },    // advisory for end users; the launcher must also check process.versions.node and print a one-line hint
  "publishConfig": { "access": "public", "provenance": true },
  "repository": { "type": "git", "url": "git+https://github.com/<owner>/JevCode.git" },
  "keywords": ["cli", "tui", "ink", "coding-agent", "jev"],
  "dependencies": {},                        // see ADOPT: ink/react are inlined by esbuild; move them to devDependencies so `npm i -g jevcode` installs 0 packages (Codex/Claude/opencode wrappers all install only their own files)
  "devDependencies": { "ink": "7.1.1", "react": "19.3.0", … }
}
```

Rationale: the shipped artefact already contains Ink and React (`meta.json`: `node_modules` 1,023,531 of 1,565,112 bytes in output; ink 168,265, react+reconciler+scheduler 435,500, yoga 153,940). Keeping them in `dependencies` would make every `npm i -g jevcode` download ~30 packages that are never loaded and widen the install-time supply chain for no benefit. The "only ink+react" constraint is about what the code depends on; it stays true. Generate `dist/THIRD_PARTY_LICENSES.txt` at build (esbuild `legalComments: 'none'` currently strips license headers, so attribution must be produced explicitly). Drop `"private": true` when publishing; keep `.npmrc engine-strict=true save-exact=true` for contributors.

### 11.2 Launcher and build

- `bin/jevcode.js`: keep `enableCompileCache()` (−12 ms on non-TUI paths, §10.2) and the `await import('../dist/jevcode.mjs')`; add a Node-version guard *before* the import (`const [maj, min] = process.versions.node.split('.').map(Number); if (maj < 22 || (maj === 22 && min < 12)) { process.stderr.write('jevcode needs Node >= 22.12 (found ' + process.version + ')\n'); process.exit(2); }`) — the only reliable place since `engines` is advisory (§2).
- `scripts/build.mjs`: `minify: true` (or `minifyWhitespace`+`minifySyntax`+`keepNames: true` if readable traces are preferred; the identifier part is unmeasured) — halves the tarball; keep `sourcemap: true` for local builds but exclude the `.map` from `files`; `define: { 'process.env.JEVCODE_VERSION': JSON.stringify(pkg.version) }` replacing the literal `VERSION`; keep the smoke step; add `npm pack --dry-run` size assertion (< 1.5 MB) and a tarball file-list assertion.
- Keep single file (constraint). If the constraint is ever relaxed, §10.4 shows a two-chunk split (`main` + `App`) is worth ~5–11 ms.

### 11.3 Install channels

1. **`npm i -g jevcode` / `npx jevcode …`** — primary. npx works because the package has a `bin` and no install scripts; detect npx (`realpath(process.argv[1])` contains `/_npx/`) to skip upgrade hints (Gemini pattern §1.4).
2. **Homebrew tap** `github.com/<owner>/homebrew-jevcode`, formula `Formula/jevcode.rb` (Node-app style, mirrors gemini-cli.rb):

```ruby
class Jevcode < Formula
  desc "Coding-agent harness where Jev decides and Claude writes the code (Ink TUI)"
  homepage "https://github.com/<owner>/JevCode"
  url "https://registry.npmjs.org/jevcode/-/jevcode-0.1.0.tgz"
  sha256 "<sha256 of the npm tarball>"
  license "MIT"

  depends_on "node"          # engines allow >=22.12 <27; use "node@22" if the range is ever narrowed

  def install
    system "npm", "install", *std_npm_args   # --global --ignore-scripts --prefix=libexec <tarball>
    bin.install_symlink libexec.glob("bin/*")
    generate_completions_from_executable(bin/"jevcode", "completion", shells: [:bash, :zsh, :fish])
    man1.install libexec/"lib/node_modules/jevcode/man/jevcode.1"
  end

  test do
    assert_match version.to_s, shell_output("#{bin}/jevcode --version")
    assert_match "run", shell_output("#{bin}/jevcode --help")
  end
end
```

Install: `brew install <owner>/jevcode/jevcode` (Homebrew auto-taps, §3). The release job rewrites `url`/`sha256` and pushes to the tap, as opencode's `publish.ts` does (§1.1). No homebrew-core submission until notability is established (UNVERIFIED thresholds, §3).
3. **GitHub Releases**: attach the npm tarball + `SHA256SUMS` for auditability; no native binaries in v0.x (SEA rejected, §10.7). Revisit SEA only if a Node-less audience appears, using the Gemini `sea-launch.cjs` shape (§1.4) with the variant-B cache extraction (§10.7).
4. **No curl installer** for now: it would only wrap `npm i -g`; the four tools' installers exist because they ship native binaries.

### 11.4 `jevcode completion <bash|zsh|fish>` design

- New command in `src/cli/args.ts` `COMMANDS` (`'completion'`) with one positional `shell` ∈ `bash|zsh|fish` (and `--install-path` that only *prints* the conventional destination). Output is a **static** script generated from the existing `FLAGS` table (commands, `--name`, `arg` enumerations such as `anthropic|openrouter`, `auto|seatbelt|none`, `swebench|terminal-bench|quixbugs|ladder|all`, `jev-on|jev-off|jev-only`; `hidden: true` flags excluded). Static beats yargs' dynamic callback because a TAB must not cost a 27 ms Node start; clap does the same (§5). Zero file reads, zero network, no stdin — it is safe before any config resolution.
- bash: `_jevcode() { local cur prev; _get_comp_words_by_ref -n : cur prev 2>/dev/null || { cur=${COMP_WORDS[COMP_CWORD]}; prev=${COMP_WORDS[COMP_CWORD-1]}; }; case $prev in --provider) COMPREPLY=($(compgen -W "anthropic openrouter" -- "$cur")); return;; --resume) COMPREPLY=($(compgen -W "$(ls "${JEVCODE_HOME:-$HOME/.jevcode/runs}" 2>/dev/null)" -- "$cur")); return;; …; esac; … }; complete -F _jevcode jevcode`. Destination printed: `${BASH_COMPLETION_USER_DIR:-${XDG_DATA_HOME:-$HOME/.local/share}/bash-completion}/completions/jevcode` (§5).
- zsh: `#compdef jevcode` + `_arguments -C '1:command:(run config bench perf completion)' '--provider[generator provider]:provider:(anthropic openrouter)' …` with a `_jevcode_runs` helper that globs `${JEVCODE_HOME:-$HOME/.jevcode/runs}/*(/:t)` for `--resume`. Destination: any `$fpath` dir, e.g. `${ZDOTDIR:-$HOME}/.zsh/completions/_jevcode` (Homebrew: `share/zsh/site-functions/_jevcode`).
- fish: `complete -c jevcode -f`; `complete -c jevcode -n __fish_use_subcommand -a run -d 'run a task'` …; `complete -c jevcode -l provider -xa 'anthropic openrouter'`; `complete -c jevcode -l resume -xa '(ls (set -q JEVCODE_HOME; and echo $JEVCODE_HOME; or echo ~/.jevcode/runs) 2>/dev/null)'`. Destination `~/.config/fish/completions/jevcode.fish` (§5).
- Run-id completion happens shell-side (a directory listing), so it never executes `jevcode` and never touches `run.json` (keys stay out of shells and logs).
- `man/jevcode.1` generated at build from the same `FLAGS` table (roff `.TH JEVCODE 1`), so `--help`, completions and the man page cannot drift.

### 11.5 `jevcode upgrade` design (network only on explicit request; never before the first frame)

- **Default: no update check at all in `run`.** The first frame contract (argv + env + `isTTY` only) stays intact; `run` never opens a socket to the registry.
- `jevcode upgrade [<version>|latest|next] [--check] [--method npm|brew|pnpm|bun|yarn]`: resolves the install method from `realpath(process.argv[1])` (`/_npx/` → npx: print "installed via npx, nothing to upgrade"; Homebrew Cellar prefix or `brew --prefix jevcode` → `brew upgrade jevcode`; `/.bun/install/global` → `bun add -g jevcode@<v>`; `/.pnpm/global` or `/.local/share/pnpm` → `pnpm add -g jevcode@<v>`; `/.yarn/global` → `yarn global add jevcode@<v>`; else `npm install -g jevcode@<v>` — never `npm update -g`, per Claude's docs §1.2). Fetches `https://registry.npmjs.org/jevcode` (`dist-tags.latest|next`) with `AbortSignal.timeout(2000)` (Gemini uses 2 s, §1.4), `User-Agent: jevcode/<version>`, no credentials; then spawns the package manager with `stdio: 'inherit'` and verifies by spawning `jevcode --version` (opencode's `verifyBinary` idea, §1.1). Exit codes: 0 upgraded/up to date, 2 usage, 5 network, 6 package-manager failure (stderr passed through).
- **Optional notifier, off by default** (`config.json` `"updateNotify": true` or `JEVCODE_UPDATE_NOTIFY=1`): after `run` finishes (never before/while the TUI renders), spawn a detached `unref()`'d `jevcode upgrade --check --write-cache` that writes `${XDG_CACHE_HOME:-~/.cache}/jevcode/update-check.json` (`{ checkedAt, latest, current }`); the *next* `run` reads that file **after** the first frame and, if newer, prints a single dim line at exit. Suppressed when any of `CI`/`CONTINUOUS_INTEGRATION` is truthy (is-in-ci semantics, §4), `NO_UPDATE_NOTIFIER`/`JEVCODE_NO_UPDATE_CHECK` is set, stdout is not a TTY or `--plain`, running via npx, or checked within 24 h. This is update-notifier's model (§4) without the dependency (Node built-ins only).
- No self-modifying installs (no downloading tarballs into `~/.local`): the package manager that installed JevCode upgrades it, so `brew`/`npm` metadata never disagrees with the binary (Claude's `DISABLE_UPDATES` and opencode's "may be managed by a package manager" prompt exist precisely because self-updates fight package managers).
- `jevcode doctor` (small, later): prints version, Node version, install method, paths (`JEVCODE_HOME`, config path), sandbox level, compile-cache status (`module.enableCompileCache()` result), completion install status — read-only, like `claude doctor`.

### 11.6 Directories

Keep `~/.jevcode/runs` (`JEVCODE_HOME`) for run state — the seatbelt profile and the resume format depend on it and three of the four tools use a dot-dir for state (§7). Honour `XDG_CONFIG_HOME` for `config.json` (`${XDG_CONFIG_HOME:-~/.config}/jevcode/config.json`; the README already advertises `~/.config/jevcode`). Put caches under `${XDG_CACHE_HOME:-~/.cache}/jevcode` (update-check file; any future extracted bundle). Never write completions or rc files from the CLI; only print destinations (opencode's installer edits rc files, Claude's binary manages `~/.local/bin` — both are sources of support issues per their docs §1.1/§1.2).

### 11.7 Release checklist

1. `npm run check` (tsc strict + `no-any`, vitest unit) and `npm run build` (bundle + first-frame smoke with `JEVCODE_ASSERT_NO_NETWORK=1`).
2. `npm run perf` → `perf/results/latest.json` `firstFrame.pass === true` (cold p95 < 300), render-lag gates, zero `\x1b[2J`.
3. `npm pack --dry-run --json` → assert exact file list (§11.1) and tarball size budget; `tar tzf` shows no `.map`, `.env`, `docs/`.
4. Version bump in `package.json` only (bundle reads it via define); `git tag v<x.y.z>`; changelog entry.
5. GitHub Actions `release.yml` on tag: `actions/setup-node` with `node-version-file: .nvmrc` and `registry-url`; `npm ci`; steps 1–3; `npm publish --access public` under **trusted publishing** (`permissions: id-token: write`; npm ≥ 11.5.1, Node ≥ 22.14 — the pinned 22.23.2 qualifies) so provenance is automatic (§9); `gh release create v<x.y.z> jevcode-<x.y.z>.tgz SHA256SUMS`.
6. Tap bump job: compute `sha256` of `https://registry.npmjs.org/jevcode/-/jevcode-<v>.tgz`, rewrite `Formula/jevcode.rb`, push to `homebrew-jevcode`; `brew install --build-from-source <owner>/jevcode/jevcode && brew test jevcode` in CI.
7. Post-publish verification from a clean container: `npx -y jevcode@<v> --version`, `npm i -g jevcode@<v> && jevcode --help`, `npm view jevcode dist.attestations`, `jevcode completion zsh | head -1` prints `#compdef jevcode`.
8. Dist-tags: pre-releases go to `next` (`npm publish --tag next`); `latest` moves only after the bench/perf gates; `jevcode upgrade next` selects the channel.

## 13. REJECT

| What not to do | Why |
|---|---|
| `node --build-snapshot` / `--snapshot-blob` for the Ink bundle | Entry runs as CJS (`Cannot use import statement outside a module`), `import()` is `Not supported` in the builder, esbuild cannot emit CJS from ink 7.1.1/yoga-layout 3.2.1 (top-level await), and `WebAssembly is not defined` in the builder; builtins-only reference shows no gain (19.1 vs 18.4 ms) — §10.6 |
| Node SEA as the shipped artefact | Works (§10.7) but 113 MB per platform, parity not speedup (80.4 ms TUI vs 80.5), `useSnapshot` impossible, `useCodeCache` incompatible with `import()`, per-platform builds on the exact Node version, codesign/notarization work; only Gemini experiments with it and none of the four ships one built from Node |
| Bun `--compile` or Rust-style native binaries via `optionalDependencies` | Requires Bun (not Node 22), 144–218 MB per platform, 6–12 platform packages, postinstall scripts and `.exe` placeholder tricks; JevCode has no native modules to justify it |
| Runtime `optionalDependencies` / `postinstall` of any kind | Adds `--ignore-scripts`/`--omit=optional` failure modes that all three binary shippers have to document and work around |
| Startup update check (network before/while the first frame renders) | Violates the first-frame contract; Claude/Gemini/opencode only do it because their UIs are already up and they accept the traffic |
| Self-updating installer that downloads into `~/.local/bin`/`~/.jevcode` | Fights `brew`/`npm` ownership (opencode's "may be managed by a package manager" prompt; Claude's `DISABLE_UPDATES` exists for this); JevCode has no binary to swap |
| Writing shell rc files or completion files from the CLI/installer | opencode's installer edits `.zshrc`/`.bashrc`; JevCode should only print destinations and let Homebrew/users install |
| Shipping `dist/jevcode.mjs.map`, `dist/meta.json`, `docs/` in the tarball | 2.5 MB map + 0.3 MB metafile + design docs triple the download for no runtime value (`files` today) |
| Depending on `update-notifier`, `xdg-basedir`, `latest-version`, `yargs`, `boxen` | Runtime-dependency constraint; every needed piece is `node:fs`, `fetch`, `AbortSignal.timeout`, `os.homedir()` |
| A curl installer (`curl … \| bash`) in v0.x | Would only wrap `npm i -g`; adds a trust surface (opencode's verifies no checksum) without a native binary to justify it |
| Code splitting (for now) | Measured gain 4–11 ms on the TUI and 5 ms on `--version` (§10.4) but breaks the single-file constraint and the `files` list; revisit if the constraint changes |
| Dynamic (yargs-style) completion callbacks | One Node process per TAB (~27 ms) |
| Telemetry of any kind on by default | Claude/Gemini default on and need three env vars to disable; JevCode already promises "keys never appear in logs" — simplest is no telemetry, or opt-in only, honouring `DO_NOT_TRACK` |

## 14. OPEN QUESTIONS

1. Policy wording: is moving `ink`/`react` to `devDependencies` (they remain the only libraries the code imports, but are inlined) acceptable under "runtime dependencies are ONLY ink and react"? If not, `npm i -g` will install ~30 unused packages.
2. `minify: true` vs `minifyWhitespace+minifySyntax+keepNames`: the identifier-mangling share of the 2 ms/1 MB win was not measured; readable stack traces for bug reports may be worth more.
3. Homebrew: `depends_on "node"` (currently Node 26.x in homebrew-core; JevCode's range allows `<27`) vs `node@22` (matches the pinned toolchain but versioned-node formulas need shebang handling). Which Node does the team want to support in the tap?
4. homebrew-core eligibility (notability thresholds not verifiable from the fetched page) — tap only until then?
5. Should `run` be allowed *any* deferred network for the notifier, or should update discovery live only in `jevcode upgrade --check`? (The design above makes it opt-in; the strictest reading of the constraint says never.)
6. Windows: no measurement was possible on this machine (harness uses `/usr/bin/script`). Does Ink 7.1.1 raw-mode + `useWindowSize()` behave in Windows Terminal/ConPTY, and does `--sandbox none` need a Windows-specific env scrub?
7. `XDG_CONFIG_HOME` support changes the config lookup path on Linux for users who set it; is a one-release fallback (`~/.config/jevcode` then `$XDG_CONFIG_HOME/jevcode`) needed?
8. Dist-tag channels (`latest`/`next`) vs Claude-style `stable`/`latest` semantics: does the bench gate define "stable"?
9. If a Node-less audience appears, SEA variant B needs a cache-integrity check (hash the extracted bundle like Gemini's `manifest.mainHash`) and a decision on notarization identity — deferred.
10. Signal exit codes: Codex re-raises the signal (`process.kill(process.pid, signal)`), Claude's fallback wrapper uses `128+signum`; JevCode's engine returns 130/143 itself — confirm the launcher never sits between them (it does not spawn, so no forwarding is needed).

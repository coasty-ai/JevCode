## Defects

1. **§10.1 / §1.3 — no arm isolates Jev; the comparison is confounded by generator hygiene.** Every wall lever in §7.2 that matters (plan-free ≤ 1,500-token output, `reasoning` off, per-sample deadline, drop-not-retry, N samples, code completion) is applied only to `llm-jev`, while `jev-off` keeps `propose_action` with a re-emitted plan, `max_tokens 4096` (`src/bench/cli.ts:36`), no deadline, and its 367 s single calls. Fix: add two arms — `jev-off-tuned` (same provider flags, deadline, `length` handling, plan-free `propose_action` if you keep the action grammar) and `llm-sieve` (LLM samples → lanes → code guard, localisation from traceback frames + SBFL, no Jev requests at all). Pre-register that `llm-jev` must beat `llm-sieve` on pass or correct-by-verdict; otherwise the Jev questions are cost.

2. **§1.3 criterion 1 is statistically unattainable on ladder and nearly so on SWE.** Exact McNemar two-sided with b wins / c losses: on ladder jev-off already solves 15/20, so the maximum discordant set is (5, 0) → p = 0.0625 > 0.05. On SWE, net +6 is significant only as (6, 0) (p = 0.031); (7, 1) gives 0.070, (8, 2) 0.109. The criterion silently requires `llm-jev` to solve a strict superset, which §11 d/k say it will not. Fix: pre-register discordant counts directly (e.g. b − c ≥ 4 and c ≤ 1 on ladder), use a one-sided sign test, or drop p-values at n = 20 in favour of Wilson intervals plus the repeat run.

3. **§1.2 / §8.3 — the ladder baseline row is wrong and the cost criterion fails by the design's own arithmetic.** Measured jev-off ladder is $0.0116/task, not $0.024; the design's `llm-jev` estimate is $0.025 → raw 2.1× (criterion 4 requires ≤ 1.0×), $/solved 1.9×. On QuixBugs §8.3 double-counts (uses jev-only's $0.0046 Jev figure although §8.2 says ≈ $0.0003/step after SKETCH/BEAM are gated), and even corrected, $/solved lands at 0.5–0.6× against a ≤ 0.5× bar. Fix: recompute §8.3 from the checked-in `summary.json` files; either cut Jev spend on ladder (skip Q2/Q3 when the module count is ≤ 10, drop Q5n Nouls at 3.3× tokens, make Q21 recorded-only) and use N = 3, or restate criterion 4 as $/solved only.

4. **§6.2 grace + Q15/Q16 arbitration is the mode's dominant correctness decision, and it is unmeasured for the pairs it will see.** With the round p50 ≈ 6 s and seeds landing at 3.8 s, the guard waits for the LLM on nearly every QuixBugs/ladder program, so seed-vs-LLM arbitration is per-program, not the rare ≥ 2-passer case. `arbitrate()` breaks Choice ties by `byEditCost` (`src/synth/search/guard.ts`) and `clusterByBehaviour` represents each cluster by its min-edit member — if the perturbation probes do not separate a one-token seed from a multi-line LLM fix, they collapse into one cluster and the seed wins without Jev being asked. Q15's 8/10 gold was measured on same-line single-token sets, not (seed line vs LLM hunk) pairs. Result: `llm-jev` inherits jev-only's overfits (2/40, 5/14) whenever the seed wins, which threatens criterion 2 on ladder (jev-off is 9/9 correct). Fix: a code rule — when an `llm` passer and a seed passer share a behaviour cluster, prefer the `llm` candidate (GLM 16/16 gold-or-equivalent vs seeds 7 overfits in 53 solves); ask Q15/Q16 only across distinct clusters; add (seed, LLM) pairs to the §10.2 probe.

5. **§5 Q17 strong fix-absent withholds LLM samples from testing exactly where testing is the only oracle.** On repository class `t_repro > 2 s` or `|distinct| > runsLeft`, so Q17 gates every round; "strong = P(escape) − p_max ≥ 0.10 ∧ max Noul < 0.3 → spend no run". Map §3 item 11 shows Jev's escape on repository states is pathological (152/160 `none_of_these`, passing line at p 0.03–0.31), the AUROC 0.916 was measured on near-duplicate single lines, and "does this multi-hunk patch make the tests pass" is a derived fact (map §3 item 1: "useless when the fact must be derived"). Fix: never skip testing on `llm` candidates; use Q17 for order only, always run top-1 (already the runner's "uncut top job"), and let the feedback round fire on 0 passers, not on Jev's escape.

6. **§4.10 / §6.6 — an LLM-written reproduction lets the LLM's misreading of the issue drive a `complete` stop.** L2 asserts *its* reading of the expected behaviour; the code filter only removes NameError/network; Q18 is measured at 18/23 on code-extracted snippets, not LLM prose. 12. **§4.3 / §11 d — Jev's localisation is a hard filter on what the LLM may fix, and its ceiling is not computed.** Listings are the anchors' ≤ 3 functions; on SWE the chained file∧function∧line top-5 was 21/30, and `need` only lets the model name symbols it can infer. ## Verdict

As written, `llm-jev` would very probably beat GLM jev-off by a wide margin on wall time and by a solid margin on pass rate on QuixBugs and ladder — but for reasons the design's measurement plan cannot attribute to Jev: the gains come from shadow-lane tests as the oracle, N small plan-free samples with deadlines against a baseline that still emits 4,096-token plans and sits through 367 s calls, and a code completion fact. Jev's roles in the happy path reduce to a 70 %-accurate line hint, a count read-back, and an arbitration whose measured accuracy does not cover the seed-vs-LLM pairs it will actually adjudicate on nearly every program; on repositories Jev's Q17 escape can withhold the only candidates that can fix anything. On cost the design fails its own criterion 4 on ladder by about 2× and is borderline on QuixBugs; on statistics, criterion 1 cannot be met on ladder and needs a strict superset on SWE. Without an `llm-sieve` (no-Jev) arm and a hygiene-matched `jev-off-tuned` arm, a passing head-to-head would demonstrate that verified LLM sampling beats unverified LLM planning — which is already the skeptic's position — and would leave "Jev adds nothing over a good LLM loop" untested.
